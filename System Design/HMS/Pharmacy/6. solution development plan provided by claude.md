আমি IMS ↔ Pharmacy স্টক-সিঙ্ক গ্যাপ নিয়ে ইতিমধ্যে করা কাজ (docs/PHAR-IMS-Stock-Replenishment-Gap.md) এবং বর্তমান কোডবেসের `InventoryReceiptService`/`IStockLedgerService`/`IPharmacyStockLedgerService` যাচাই করেছি — নিচে সম্পূর্ণ আর্কিটেকচার প্ল্যান দিলাম। **কোনো কোড লেখা হয়নি**, শুধু বিশ্লেষণ ও প্রস্তাব।

## TL;DR

সুখবর: এই ফিচারের জন্য **নতুন টেবিল/মাইগ্রেশন লাগবে না**। `PharmacyItemStock`, `PharmacyStockMovement`, `IPharmacyStockLedgerService`, এমনকি `EnumPharmacyStockMovementType.TransferIn` আর `EnumPharmacyStockReferenceType.InventoryReceipt` enum ভ্যালু পর্যন্ত — সব আগেই বানানো আছে ঠিক এই ইন্টিগ্রেশনের জন্য (Phase 6/7-এ, ২৯-৩০ জুলাই)। যা নেই তা হলো শুধু একটা **wiring/plumbing স্তর**: `InventoryReceiptService.ConfirmAsync`-এর একটামাত্র stock-increase কল-সাইটকে destination-aware করা।

## ১. Integration Point — কোথায় হুক করবো

**`InventoryReceiptService.ConfirmAsync`** (`HMS.Services/Areas/IMS/InventoryReceiptService.cs:32-115`) — Confirm/Receive-এর মুহূর্তটাই সঠিক জায়গা, অন্য কোনোটা না। কারণ:

- এটাই একমাত্র জায়গা যেখানে ownership সত্যিকার অর্থে **destination** ওয়্যারহাউসে transfer হয় (`_stockLedgerService.IncreaseStockAsync(...)`, লাইন 62-66)।
- `InventoryTransferService`-এর Confirm/Dispatch ধাপ (source থেকে stock কমানো) অপরিবর্তিত থাকবে — Central Warehouse থেকে stock বের হওয়াটা সবসময়ই IMS-এর নিজের দায়িত্ব, destination যাই হোক না কেন। ব্যবসায়িক ডিজাইনের সাথে হুবহু মিলে যায়: "IMS দায়িত্ব শুধু Central Warehouse-এর"।
- Transfer আর Receipt আলাদা ট্রানজ্যাকশনে কনফার্ম হয় (dispatch আলাদা সময়ে, receive আলাদা সময়ে) — তাই "Pharmacy আপডেট ব্যর্থ হলে rollback" প্রশ্নের সঠিক স্কোপ হলো **শুধু Receipt Confirm-এর ট্রানজ্যাকশন**, পুরো Request→Transfer→Receipt চেইন না। এটা ইতিমধ্যেই ডিজাইনে লক করা আছে (`docs/IMS-Inventory-Request-Transfer-Design.md`)।

## ৪. Transaction Safety

`ApplicationDbContext` **Transient** (প্রতিটা UnitOfWork নিজস্ব DbContext/connection পায় — `hms-dbcontext-transient-transactions` memory)। তাই Pharmacy-র repo সরাসরি DI দিয়ে ইনজেক্ট করলে সেটা **আলাদা connection**-এ চলে যাবে — একই বাগ যেটা Sale/Payment Confirm-এ দুইবার ধরা পড়েছিল (30s timeout + orphan row, `pharmacy-sale-feature-design.md` §"RUNTIME VERIFICATION")।

**সমাধান (প্রমাণিত প্যাটার্ন, নতুন কিছু না):** `IInventoryReceiptUnitOfWork` নিজের উপর দুইটা নতুন property যোগ করবে — `PharmacyItemStockRepository`/`PharmacyStockMovementRepository`, দুটোই `InventoryReceiptUnitOfWork`-এর নিজস্ব `_ctx` দিয়ে তৈরি (ঠিক যেভাবে এখন `ItemStockRepository`/`StockMovementRepository` তৈরি হয়, লাইন 19-23)। ফলে Pharmacy-র লেখাটাও **একই DbContext, একই ট্রানজ্যাকশনে** পড়ে — `ConfirmAsync`-এর বিদ্যমান `BeginTransaction()`/`CompleteAsync()`/`CommitAsync()` ব্লকের ভেতরেই, কোনো নতুন transaction machinery ছাড়াই।

**যদি Pharmacy-তে লেখা ব্যর্থ হয় (যেমন: Exp mismatch, বা Product Drug না):** বিদ্যমান `catch { await tx.RollbackAsync(); throw; }` (লাইন 108-112) পুরো Receipt Confirm-কে rollback করবে — Receipt `Pending`-এই থেকে যাবে, retryable, discrepancy log কিছুই লেখা হবে না। **Transfer (Dispatch) অপরিবর্তিত থাকবে** — সেটা আগেই আলাদা transaction-এ কমিট হয়ে গেছে; শুধু Receipt Confirm আবার চেষ্টা করা যাবে। Retry logic আলাদা করে বানানোর দরকার নেই — এটাই স্বাভাবিক retry, যেমনটা এখনই ItemStock-পথে কাজ করে।

## ৫. Future Extensibility — OT/ICU/Lab/Ward/CSSD/Emergency

`ITransferOriginValidator`-এর ঠিক একই শেপ মিরর করে নতুন ইন্টারফেস:

```
IReceiptDestinationHandler
  Task<bool> CanHandleAsync(Guid destinationWarehouseId)
  Task ReceiveLineAsync(IInventoryReceiptUnitOfWork uow, Guid warehouseId, Guid productId,
                         string batchNo, DateTime? exp, double qty, Guid referenceId, Guid actedById)
```

- **`PharmacyReceiptDestinationHandler`** (`HMS.Services/Areas/PHAR/`) — `CanHandleAsync` = destination-Id `IPharmacyWarehouseService.GetDefaultWarehouseAsync().Id`-এর সমান কিনা চেক করে; `ReceiveLineAsync` = Drug resolve করে `IPharmacyStockLedgerService.IncreaseStockAsync` কল করে।
- **`DefaultItemStockReceiptHandler`** (`HMS.Services/Areas/IMS/`) — বাকি সবার জন্য ফলব্যাক, আজকের বিদ্যমান আচরণ (`IStockLedgerService`) হুবহু ধরে রাখে।
- `InventoryReceiptService`-এর constructor নেয় `IEnumerable<IReceiptDestinationHandler> specificHandlers` + একটা আলাদা `IReceiptDestinationHandler defaultHandler` (দুইটা আলাদা DI স্লট, registration-order-এর উপর নির্ভর না করে) — যাতে ভুল ক্রমে রেজিস্টার করলে নীরবে আবার ভুল ledger-এ চলে যাওয়ার ঝুঁকি না থাকে।

**ফলাফল:** ভবিষ্যতে OT/ICU/Lab/Ward/CSSD-এর জন্য নতুন handler ক্লাস + Startup.cs-এ এক লাইন DI registration — `InventoryReceiptService`-এর একটা লাইনও বদলাবে না। ঠিক যেমন ব্যবসায়িক স্পেসিফিকেশনে চাওয়া হয়েছে: "শুধু destination module পরিবর্তন হবে"।

**"Notify" শব্দটার ব্যাখ্যা:** HMS-এ এখনো কোনো message-bus/async-notification পরিকাঠামো নেই (আগের অনুসন্ধানেও নিশ্চিত হয়েছে)। তাই "Pharmacy module-কে notify করা" এখানে মানে **synchronous, একই-ট্রানজ্যাকশনের ভেতরে সরাসরি ইন-প্রসেস কল** — asynchronous event/webhook না। এটাই এই প্রজেক্টের প্রতিটা আগের cross-module integration-এর প্যাটার্ন (PHAR UoW-তে ACC repo bundling, ইত্যাদি)।

## ৬. Implementation Plan

### আর্কিটেকচার ডায়াগ্রাম

```
InventoryReceiptService.ConfirmAsync
        │
        ├─ destinationWarehouseId = receipt.InventoryTransfer.DestinationWarehouseId
        ├─ handler = ResolveHandler(destinationWarehouseId)   // specificHandlers.FirstMatch ?? defaultHandler
        │
        └─ foreach item in receipt.InventoryReceiptItems:
                await handler.ReceiveLineAsync(_unitOfWork, destinationWarehouseId,
                        item.ProductId, item.BatchNo, item.Exp, receivedQty, receipt.Id, userId)
                        │
                        ├─ PharmacyReceiptDestinationHandler
                        │     → Drug = IDrugRepository.GetByProductIdAsync(productId)
                        │     → null? throw BusinessRuleException
                        │     → IPharmacyStockLedgerService.IncreaseStockAsync(
                        │           _unitOfWork, _unitOfWork.PharmacyItemStockRepository,
                        │           _unitOfWork.PharmacyStockMovementRepository, ...)
                        │
                        └─ DefaultItemStockReceiptHandler (ফলব্যাক, আজকের আচরণ)
                              → IStockLedgerService.IncreaseStockAsync(
                                    _unitOfWork, _unitOfWork.ItemStockRepository,
                                    _unitOfWork.StockMovementRepository, ...)
        │
        └─ একই BeginTransaction()/CommitAsync() ব্লক — সব-বা-কিছুই-না
```

### Sequence (Confirm একবার কল হলে)

1. Receipt লোড, Status == Pending চেক (অপরিবর্তিত)
2. Transaction শুরু
3. Destination Warehouse-Id থেকে handler resolve (একবার, লুপের বাইরে)
4. প্রতি line-এর জন্য: qty resolve → discrepancy চেক (অপরিবর্তিত) → `handler.ReceiveLineAsync(...)`
5. Receipt.Status = Received, StatusLog লেখা (অপরিবর্তিত)
6. Commit — ব্যর্থ হলে সম্পূর্ণ rollback (Receipt আবার Pending, retryable)
