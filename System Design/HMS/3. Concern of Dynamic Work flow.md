আপনার existing system দেখে design টা এখন concrete ভাবে যাচাই করতে পারছি। কয়েকটা গুরুত্বপূর্ণ জিনিস বেরিয়ে এল যা আপনার ERD এর সাথে বাস্তবের পার্থক্য তৈরি করে:

- আপনার system এ **Role = ASP.NET Identity** (`ApplicationRole`), আর User↔Role হলো **many-to-many** (`ApplicationUserRole`) — আপনার ERD তে যেমন `User.RoleId` (এক user = এক role) দেখানো, বাস্তবে তা নয়।
- Amount = `Purchase.TotalPrice` (items থেকে recompute হয়) এবং PR **multi-currency** (`CurrencyId` আছে)।
- বর্তমান `EnumPurchaseRequisitionStatus` = `Inactive/Draft/Final/Completed` — **কোনো approval state নেই**।

এখন নিচে আমি gap আর use-case গুলো সাজিয়ে দিলাম। এগুলোকে ৩ ভাগে ভাগ করেছি: **কোডিং এর আগে অবশ্যই ঠিক করতে হবে**, **ঠিক করলে ভালো**, আর **ভবিষ্যতের জন্য park**। প্রতিটার সাথে আমার recommendation দিয়েছি — আপনি শুধু হ্যাঁ/না বা বিকল্প বললেই হবে।

## 🔴 A. অবশ্যই ঠিক করতে হবে (এগুলো ছাড়া code লেখা যাবে না)

**A1. Approver = Role, কিন্তু Role এ অনেক User থাকে** Stage এ `RoleId` আছে, তাই "Manager role" এর **যেকোনো একজন** user approve করলেই stage pass হবে — এটাই কি চান? (Alternative: নির্দিষ্ট user assign করা।)

- ➤ Recommendation: **Role-based** — role এর যেকোনো একজন approve করলে stage complete। (Flexible, future-proof)
- ⚠️ Sub-issue: সেই role এ যদি **কোনো user না থাকে** → PR চিরতরে আটকে যাবে (deadlock)। Policy/workflow activate করার সময় validate করতে হবে।

**A2. Self-approval / Segregation of Duties** PR এর creator যদি নিজেই Manager role এ থাকে — সে কি নিজের PR approve করতে পারবে?

- ➤ Recommendation: **না** — creator নিজের PR এর কোনো stage approve করতে পারবে না। (Standard control)

**A3. Currency** Policy range (১ লক্ষ / ১০ লক্ষ) কোন currency তে? PR অন্য currency তে হলে amount কীভাবে compare হবে?

- ➤ Recommendation: এখন যদি সব PR এক base currency (BDT) তে হয় — policy সেই base currency তে ধরব। যদি multi-currency সত্যিই ব্যবহার হয়, তাহলে PR amount কে base currency তে convert করে তারপর policy match করতে হবে। **আপনি বলুন — এখন কি সব PR একই currency তে?**

**A4. Amount পরিবর্তন হলে (items edit) → workflow পুনর্মূল্যায়ন** PR ছিল ৯০,০০০ (single approver), edit করে ৫,০০,০০০ (Manager লাগবে) হলো — মাঝপথে amount বাড়লে/কমলে কী হবে?

- ➤ Recommendation: PR **Draft** অবস্থায় amount বদলালে সমস্যা নেই (submit এর সময় workflow assign হবে)। কিন্তু **approval শুরু হওয়ার পর amount বদলানো block** করব, অথবা বদলালে approval **reset** হয়ে নতুন workflow দিয়ে আবার stage-1 থেকে শুরু হবে। **কোনটা চান?**

**A5. State machine (Status enum বাড়াতে হবে)** বর্তমান enum এ approval state নেই। আমার প্রস্তাব — নতুন states: `Draft → PendingApproval → Approved → Rejected → Cancelled` (আর mid-flow এ `Returned` লাগলে বলুন)।

- ➤ `CurrentStageNo`: pending stage নির্দেশ করবে; সব stage শেষ হলে `Status = Approved`।
- **প্রশ্ন:** existing `Final`/`Completed` কি রাখব নাকি নতুন approval-states দিয়ে replace/extend করব?

**A6. Reject করলে কী হবে? (Return vs Reject)** Sequential flow এ কোনো stage reject করলে:

- (a) পুরো PR **Rejected** → creator কে আবার নতুন PR/resubmit করতে হবে, নাকি
- (b) **Returned** → creator edit করে resubmit করবে, তখন approval **stage-1 থেকে আবার শুরু**?
- ➤ Recommendation: reject করলে full **Rejected**; creator resubmit করলে **stage-1 থেকে নতুন করে** (নতুন approval cycle)। **আপনি কি একমত?**

## 🟡 B. ঠিক করলে ভালো (code এর structure ঠিক রাখতে দরকার)

**B1. Workflow snapshot vs live-edit** `WorkflowId` শুধু reference হিসেবে PR তে আছে — stage গুলো copy করা নেই। Admin যদি চলমান PR থাকা অবস্থায় workflow এর stage বদলায়, তাহলে in-flight PR ও প্রভাবিত হবে।

- ➤ Recommendation: **`ApprovalWorkflow` versioning** অথবা PR তৈরির সময় stage-list **snapshot** করা। সরল সমাধান: workflow active থাকলে edit না দিয়ে "নতুন version" বানানো। (এটা future safety এর জন্য গুরুত্বপূর্ণ।)

**B2. `IsMandatory` এর মানে কী?** Sequential flow এ non-mandatory stage মানে কী? — action না নিলে auto-skip? নাকি optional reviewer?

- ➤ Recommendation: শুরুতে **সব stage mandatory** ধরে flag টা future এর জন্য রাখি; optional/skip logic এখন implement না করি। (সরল রাখতে)

**B3. StageNo গ্যাপ থাকলে** Stage 1,2,3 না হয়ে 1,3,5 হলে? — "next stage" logic টা `CurrentStageNo + 1` না করে **StageNo অনুযায়ী পরের stage** খুঁজবে।

- ➤ Recommendation: order-by-StageNo দিয়ে next stage বের করব (safe)।

**B4. Concurrency (double-approval)** একই stage এ দুই Manager একসাথে approve চাপলে stage দুবার advance হতে পারে।

- ➤ Recommendation: PR এ **RowVersion / optimistic concurrency** দিয়ে guard করব।

**B5. PRApproval row — আগে বানাব নাকি action এর সময়?** সব stage এর pending row আগে বানাব, নাকি approve করলে তখন row তৈরি হবে?

- ➤ Recommendation: **action এর সময় log** করব (approve/reject হলেই row)। "কে pending" তা workflow stage + CurrentStageNo থেকেই বের হবে। (কম clutter)

## B1 আর B3 — এখানে একটা অসঙ্গতি আছে, এটা আগে ঠিক করি

আপনার **B1 = Immutable Workflow (whole workflow clone)** আর **B3 = individual stage edit → new entry** — এই দুটো আসলে **দুই level এর versioning**, একসাথে রাখলে গোলমাল হবে।

- **B1 (আমি এটাই strongly recommend করি):** পুরো **Workflow** immutable। কিছু বদলাতে হলে **পুরো workflow clone** → পুরনোটা `Archived`, নতুনটা `Active`। WorkflowId নিজেই version।
- **B3:** শুধু একটা **Stage** edit করলে সেটা নতুন row হবে — এটা **stage-level** versioning।

**দুটো একসাথে দরকার নেই — B1 নিলে B3 এর সমস্যা নিজে থেকেই মিটে যায়।** কারণ:

> Immutable workflow এ আপনি কখনো একটা single stage আলাদা করে edit করবেন না। যেকোনো পরিবর্তন = পুরো workflow clone করে নতুন stage-set বানানো। ফলে একটা workflow এর ভেতর StageNo সবসময় **পরপর (1,2,3)** থাকবে — গ্যাপ তৈরি হওয়ার সুযোগই নেই।

তাই আমার প্রস্তাব: **শুধু B1 (workflow-level immutability) নিন, B3 বাদ দিন।** আর engine এ next-stage বের করব `ORDER BY StageNo` দিয়ে (defensive, তবু নিরাপদ)।

এর ফলে `ApprovalWorkflow` টা এমন হবে:

```
ApprovalWorkflow: WorkflowId, WorkflowName, Status (Draft / Active / Archived)
```

(IsActive bool এর বদলে একটা `Status` — Draft = বানানো হচ্ছে, Active = publish করা, Archived = পুরনো version)

Flow: নতুন workflow → **Draft** এ stage যোগ করুন → **Publish** (Active, এরপর immutable) → পরিবর্তন লাগলে **Clone** → পুরনোটা Archived।

> Note: `ApprovalPolicy` কিন্তু mutable থাকবে — clone করার পর policy টা নতুন Active WorkflowId এ re-point করবেন। কিন্তু চলমান PR তার `WorkflowId` submit এর সময়ই snapshot করে রাখে, তাই সে পুরনো (Archived) workflow দিয়েই চলবে। এটাই আপনার চাওয়া immutability। ✅

**আপনি কি B3 বাদ দিয়ে শুধু B1 (immutable workflow + clone) তে একমত?**
