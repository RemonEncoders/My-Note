## এখনকার design-এর মূল সমস্যা

**"এই item-টা কী?" — এই প্রশ্নের উত্তর এখন দুই জায়গায়, আর দুটো মিলে নাও থাকতে পারে:**

1. `Product.ItemType` — কিন্তু এটা ঠিক হয় **কোন পেজ থেকে entry হয়েছে** তার ভিত্তিতে (Add পেজ → Product, AddService পেজ → Service)। ডেটা নিজে কিছু বলে না।
2. `Category.CategoryType` — কিন্তু user চাইলে Add পেজে (ItemType=Product) গিয়ে "Technical Services" category বেছে নিতে পারে। তখন item বলছে "আমি পণ্য", category বলছে "আমি সেবা" — **কেউ আটকাবে না।**

মানে: **single source of truth নেই।** নতুন ধরন (যেমন Asset) যোগ করতে চাইলে নতুন পেজ + enum change + সব জায়গায় hardcoded logic — এভাবে scale করে না।

## Best Design: ধরনটা Category-র মধ্যে রাখুন, Product সেটা উত্তরাধিকারে পাবে

ERP জগতে (SAP MM — যেটার আদলে আপনার ValuationClass, Batch ইত্যাদি বানানো) এই সমস্যার সমাধান হলো: **item-এর nature একটা master data হবে, আর সেটা behavior flag বহন করবে।** আমার প্রস্তাব:

```
┌──────────────────┐        ┌──────────────────┐        ┌──────────────┐
│   ItemNature     │ 1    * │    Category      │ 1    * │   Product    │
│ (lookup table)   │◄───────│                  │◄───────│              │
├──────────────────┤        ├──────────────────┤        ├──────────────┤
│ Id               │        │ Id               │        │ Id           │
│ Name  (Product/  │        │ Name, Code       │        │ CategoryId ★ │
│  Service/Asset..)│        │ ItemNatureId ★   │        │ ItemType     │
│ IsStockManaged   │        │ ParentCategoryId │        │  (derived,   │
│ IsValuated       │        │ ValuationClassId │        │   cache only)│
│ IsSaleable       │        │ PurchaseVat, Vat │        │ MinQty/MaxQty│
│ IsPurchasable    │        └──────────────────┘        │ VED ...      │
└──────────────────┘                                    └──────────────┘
```

**মূল নীতিগুলো:**

1. **`ItemNature` একটা lookup টেবিল** (enum নয়) — seed করা থাকবে: Product, Service, Asset, Material। আপনি বলেছেন _"or whatever I wanted"_ — নতুন ধরন লাগলে শুধু একটা row insert করবেন, কোনো code change/deploy লাগবে না।
    
2. **ধরন নয়, behavior flag দিয়ে decision নিন।** UI/logic কখনো জিজ্ঞেস করবে না "এটা কি Product?" — জিজ্ঞেস করবে **"এটা কি `IsStockManaged`?"**
    
    - `IsStockManaged = true` → MinimumQty, MaximumQty, VED, Opening Stock দেখাও + required করো
    - `IsValuated = true` → ValuationClass required
    - এভাবে Asset যোগ করলে (IsStockManaged=true, IsSaleable=false) সব form আপনা-আপনি ঠিক আচরণ করবে — নতুন if/else লিখতে হবে না।
3. **প্রতিটা Category ঠিক একটা ItemNature-এর অধীনে থাকবে** (`ItemNatureId` required)। Category তখন pure classification tree — "Finished Goods", "Consumable Goods" থাকবে Product nature-এর নিচে; "Technical Services" থাকবে Service-এর নিচে।
    
4. **Product-এর ধরন আসবে তার Category থেকে** — save করার সময় server নিজে `Product.ItemType = Category.ItemNature` set করবে (পেজ অনুযায়ী hardcode নয়)। ফলে item আর category-র মধ্যে **mismatch হওয়া অসম্ভব।** `ItemType` কলামটা রাখতে পারেন query-র সুবিধার জন্য denormalized cache হিসেবে, কিন্তু truth থাকবে Category-তে।
    
5. **UI flow:** Add পেজে user আগে Category বাছবে → dropdown option-এর সাথে `data-stock-managed="true/false"` থাকবে → JS দিয়ে conditional field গুলো show/hide + required toggle হবে। আলাদা Add/AddService পেজেরও আর দরকার থাকে না — এক পেজেই সব।
    

## আপনার এখনকার কোড থেকে যাওয়ার রাস্তা (দুই ধাপে)

**ধাপ ১ — কোনো schema change ছাড়াই (কম ঝুঁকি, এখনই করা যায়):**

- `EnumCategoryTypes`-কেই item nature হিসেবে ব্যবহার করুন, দরকারে `Asset` যোগ করুন
- Product save-এর সময় `ItemType` পেজ থেকে না নিয়ে Category-র `CategoryType` থেকে derive করুন
- Seed data ঠিক করুন ([SCMSeedModel.cs:107-115](vscode-webview://0tri44ar51et483btke71i178mqksugck1rce8n1q6b1u371eioe/HMS.Web/Areas/SCM/Models/SCMSeedModel.cs#L107-L115) — "Finished Goods" এখন ভুল করে Material type)
- Category dropdown-এ nature-এর তথ্য পাঠিয়ে ৩টা field conditional করুন (আপনার মূল requirement)

**ধাপ ২ — ভবিষ্যতে extensibility লাগলে:**

- `ItemNature` lookup টেবিল + behavior flags-এ migrate করুন, enum তুলে দিন

**Trade-off সংক্ষেপে:** enum রাখলে code সহজ, compile-time safety — কিন্তু নতুন ধরন মানেই deploy। Lookup table রাখলে runtime-এ নতুন ধরন যোগ করা যায় — কিন্তু একটু বেশি join/complexity। আপনি যেহেতু বলছেন ভবিষ্যতে ইচ্ছামতো ধরন চান, আমার recommendation **ধাপ ১ এখনই করুন, ধাপ ২ তখনই করুন যখন সত্যিই ৪-৫টার বেশি ধরন লাগবে।**

আপনি বললে আমি ধাপ ১ implement করে দিতে পারি — সাথে আগের সেই দুটো bug fix-ও (৩টা নতুন field এখন `AddAsync`/`UpdateAsync`/`Init(id)`-তে map হয় না, মানে save-ই হচ্ছে না)। কোনটা দিয়ে শুরু করব?
