# 09 · Key Concepts Explained

এই ফাইলে design-এর সবচেয়ে গুরুত্বপূর্ণ ও বিভ্রান্তিকর ধারণাগুলো বিস্তারিত।

---

## 1. Immutable Workflow (Enterprise Best Practice) — B1

আলাদা `Version` column রাখার বদলে **Workflow Definition-কেই immutable** রাখা হয়।

> **নিয়ম:** Workflow একবার **Published** হলে আর edit করা যাবে না। পরিবর্তন মানেই **Clone Workflow**।

**উদাহরণ:**

| WorkflowId | WorkflowName | Status |
|---|---|---|
| 3 | High Value Approval | Archived |
| 4 | High Value Approval | Published |

এখানে `WorkflowId`-ই version-এর কাজ করছে:
- Workflow 3 = পুরনো definition
- Workflow 4 = নতুন definition

তাই `Purchase`-এ শুধু `WorkflowId` snapshot রাখলেই যথেষ্ট — আলাদা `Version` column লাগে না।

**কেন এই design:**
- Workflow definition কখনো বদলায় না (immutable) → audit সহজ।
- চলমান PR কখনো নতুন rule দ্বারা প্রভাবিত হয় না।
- Code সহজ — `Purchase.WorkflowId` থেকেই সব stage বের করা যায়।

**Lifecycle:** নতুন workflow → **Draft**-এ stage যোগ → **Publish** (Published, এরপর immutable) → পরিবর্তন লাগলে **Clone** → পুরনোটা **Archived**।

> **Note:** `ApprovalPolicy` কিন্তু **mutable** থাকবে — clone করার পর policy-টা নতুন Published WorkflowId-তে re-point করা হয়। কিন্তু চলমান PR তার `WorkflowId` submit-এর সময়ই snapshot করে রাখে, তাই সে পুরনো (Archived) workflow দিয়েই চলে। এটাই কাঙ্ক্ষিত immutability। ✅

## 2. ApprovalPolicy ≠ PRApproval (সবচেয়ে বড় confusion)

অনেকে ভাবে এই দুই table-এর মধ্যে Foreign Key সম্পর্ক থাকবে। **আসলে নেই।**

- `ApprovalPolicy` হলো একটা **Rule/Configuration table**। এর একমাত্র কাজ:

```
Amount + Currency
      ↓
Workflow নির্বাচন
      ↓
PurchaseRequest.WorkflowId সেট করা
```

- এরপর পুরো approval process চালায়: **ApprovalWorkflow → ApprovalWorkflowStage → PurchaseApproval**।
- `ApprovalPolicy`-এর সাথে `PurchaseApproval`-এর **কোনো direct FK নেই**।

---

## 3. WorkflowId Snapshot — কেন গুরুত্বপূর্ণ

Submit-এর সময় `Purchase.WorkflowId` **snapshot** হয়। এর ফলে:
- পরে policy বা workflow বদলালেও **in-flight PR অপরিবর্তিত** থাকে।
- Immutable workflow + snapshot = চলমান PR সবসময় তার শুরুর rule দিয়েই শেষ হয়।

## 4. Table Relationships (1 : Many)

| Parent | Child | মানে |
|---|---|---|
| ApprovalWorkflow | PurchaseRequest | একটা workflow অনেক PR-এ ব্যবহৃত |
| ApprovalWorkflow | ApprovalWorkflowStage | একটা workflow-এর অনেক stage |
| PurchaseRequest | PRApproval | একটা PR-এর অনেক approval record |
| ApprovalWorkflowStage | PRApproval | একটা stage definition অনেক PR-এর history-তে |
| ApplicationRole | ApprovalWorkflowStage | একটা role অনেক stage-এ |

---

## 5. Role-based Approval — deadlock ঝুঁকি (A1)

Stage একটা **Role**-এর সাথে বাঁধা, নির্দিষ্ট user-এর নয়। ফলে সেই role-এর যেকোনো একজন approve করলেই stage complete।

> ⚠️ **ঝুঁকি:** কোনো stage-এর role-এ যদি একজনও active user না থাকে → PR চিরতরে আটকে (deadlock)। তাই submit/publish-এর সময় validate করতে হবে (দেখুন [08](<08. Guards and Validation.md>))।
