Claude-এর নতুন review-টি গুরুত্বপূর্ণ এবং বেশিরভাগ ক্ষেত্রে সঠিক, কিন্তু তার দুইটি মূল recommendation আমি সরাসরি গ্রহণ করব না:

1. `CoverageDecisionAudit`-কে `CoverageSnapshot` এবং `BenefitEntitlement`—সবকিছুর একমাত্র table বানানো।
    
2. `CoverageDecisionAudit`-এর প্রতিটি resolver-call-এ row তৈরি করা।

অর্থাৎ, তিনটি concept-এর মধ্যে BenefitEntitlement বাদ যাবে; কিন্তু Snapshot এবং Audit পুরোপুরি merge হবে না।

# 2. আমার recommended model

## Final conceptual structure

```
Coverage Resolver
      │
      ├── Coverage Decision
      │       │
      │       ├── EligibleCorporate
      │       ├── EligiblePartialCorporate
      │       ├── AgreementExpired
      │       ├── RelationshipNotEligible
      │       ├── PackageNotCovered
      │       ├── QuotaExhausted
      │       └── RequiresOperatorDecision
      │
      ├── HckCoverageDecisionAudit
      │       └── Decision attempt/history
      │
      └── If successfully confirmed
              │
              ├── HckScreeningCoverageSnapshot
              │       └── Immutable resolved booking coverage
              │
              ├── Invoice
              │       └── Final financial truth
              │
              └── QuotaLedger
                      └── Actual quota reservation/consumption
```

এখানে:

- `HckCoverageDecisionAudit` = decision history
    
- `HckScreeningCoverageSnapshot` = confirmed booking-এর frozen coverage context
    
- `Invoice` = final financial truth
    
- `QuotaLedger` = quota movement truth
    
- `BenefitEntitlement` = V1-এ আলাদা persisted table নয়; resolver-এর domain output হিসেবে থাকবে

# 4. কেন Snapshot এবং Audit আলাদা রাখব?

এখানে সবচেয়ে গুরুত্বপূর্ণ কারণ হলো lifecycle এবং cardinality।

## CoverageDecisionAudit-এর cardinality

একটি booking-এর জন্য একাধিক meaningful decision attempt হতে পারে:

```
Booking #1001
   │
   ├── Attempt 1: CorporateDenied - AgreementExpired
   ├── Attempt 2: CorporateDenied - QuotaExhausted
   └── Attempt 3: SelfPaySelected
```

অথবা:

```
Booking #1001
   │
   ├── Attempt 1: RequiresOperatorDecision
   └── Attempt 2: EligiblePartialCorporate
```

অন্যদিকে Snapshot:

```
Booking #1001
   └── One final confirmed coverage snapshot
```

তাই:

```
One Screening → Many meaningful CoverageDecisionAudit rows
One Screening → Zero or One confirmed CoverageSnapshot
```

এই cardinality দুটো এক নয়।

যদি একই table-কে দুটো কাজ করানো হয়, তাহলে প্রশ্ন উঠবে:

- কোন row final resolved snapshot?
    
- কোন row merely failed attempt?
    
- কোন row invoice-এর সাথে reference করবে?
    
- কোন row quota reservation-এর basis?
    
- কোন row operator correction?
    
- কোন row technical retry?
    

এগুলো solve করা সম্ভব, কিন্তু unnecessary complexity তৈরি হবে।

এখানে আমার recommendation একটু আলাদা।


এগুলো অবশ্যই থাকবে, কারণ Invoice হলো financial source of truth।

## Invoice-এর corporate context fields

এখানে দুইটি acceptable design আছে:

### Option A — Invoice → CoverageSnapshot

```
Invoice
   └── CoverageSnapshotId
```

এবং Snapshot থেকে:

- AgreementId
    
- MembershipId
    
- FamilyRelationshipId
    
- BenefitPolicyId
    
- PackageId
    

পাওয়া যাবে।

### Option B — Invoice → DecisionAudit

```
Invoice
   └── CoverageDecisionAuditId
```

কিন্তু আমি Option A বেশি পছন্দ করি, কারণ Invoice-এর সাথে সম্পর্কিত record হওয়া উচিত final successful resolved snapshot—কোনো arbitrary audit attempt নয়।

তাই:

```

```

অথবা:

```
HckScreeningCoverageSnapshot.InvoiceId
```

এর মধ্যে একটি relationship রাখা যায়।

যেহেতু আগের design-এ `Screening.InvoiceId` already আছে, তাই V1-এ খুব বেশি bidirectional FK না রাখাই ভালো।

```
HckScreening

```


এটিও সম্ভব।

### Source of truth clarification

- `Invoice.PayerType` = final payer classification
    
- `Invoice.CorporatePayableAmount` = final corporate payable amount
    
- `Invoice.PatientPayableAmount` = final patient payable amount
    
- `CoverageSnapshot` = why/how this payer split was resolved
    
- `CoverageDecisionAudit` = decision history
    
- `QuotaLedger` = quota movement
    

# 7. Claude-এর “প্রতিটি resolver-call-এ audit row” recommendation

এটি আমি পুরোপুরি গ্রহণ করব না।

কারণ resolver-call সবসময় business decision নয়।

একটি resolver অনেকবার call হতে পারে:

- User page refresh করল
    
- Dropdown পরিবর্তন করল
    
- Package change করল
    
- AJAX preview চালাল
    
- Confirm button double-click হলো
    
- Technical retry হলো
    
- Background validation হলো
    
- Same input পুনরায় evaluate হলো
    

প্রতিটি call-এ audit row তৈরি করলে audit table noise-এ ভরে যাবে।

## আমার rule হবে

> Every meaningful coverage decision attempt—not every technical resolver invocation—may create an audit record.

### Audit তৈরি হবে যখন:

- Confirmation attempt করা হয়েছে
    
- Corporate coverage resolve হয়েছে বা denied হয়েছে
    
- Operator decision দরকার হয়েছে
    
- Corporate থেকে self-pay override হয়েছে
    
- Coverage policy/eligibility decision materially changed হয়েছে
    
- Authorized operator manual resolution করেছে
    

### Audit তৈরি হবে না যখন:

- সাধারণ draft page load
    
- UI preview
    
- একই input-এর harmless recalculation
    
- technical validation call
    
- no-op retry
    
- incomplete form state
    

এতে audit meaningful থাকবে।

# 9. Gap 2: EffectiveTo retroactive restriction

Claude-এর এই recommendation আমি গ্রহণ করছি, তবে সামান্য refine করে।

Claude বলেছে:

> EffectiveTo এমন past date-এ set করা যাবে না যা confirmed booking-এর resolved context invalid করে।

এটি একটি ভালো business invariant, কিন্তু সরাসরি “কোনো confirmed booking থাকলে past date edit নিষিদ্ধ”—এভাবে universal rule করা কিছু ক্ষেত্রে অতিরিক্ত কঠিন হতে পারে।

## আমার recommended rule

### Normal policy amendment

- Existing policy row in-place update নয়
    
- Existing row-এর `EffectiveTo` set হবে
    
- New policy row তৈরি হবে
    
- Old confirmed bookings re-evaluate হবে না
    

### Retroactive change

Confirmed booking-এর coverage validity নষ্ট করে এমন retroactive amendment:

- সাধারণ edit operation-এ নিষিদ্ধ
    
- বিশেষ authorized correction workflow ছাড়া করা যাবে না
    
- correction করলে historical booking, invoice এবং audit impact review করতে হবে
    
- existing financial record silently rewrite করা যাবে না
    

অর্থাৎ:

> No ordinary retroactive policy mutation that invalidates already-confirmed booking context.

তবে legal/compliance correction-এর জন্য future-এ আলাদা controlled correction process রাখা যেতে পারে।

# 10. Gap 3: Reserved quota-এর ultimate fallback

এখানে Claude-এর Option B আমি গ্রহণ করছি, কিন্তু `Abandoned` নামটি একটু সতর্কতার সাথে ব্যবহার করব।

## আমার সিদ্ধান্ত

চিরকাল Reserved রেখে দেওয়া যাবে না।

কারণ এতে:

- quota permanently blocked হতে পারে
    
- operational failure-এর কারণে patient unfairly affected হবে
    
- annual quota availability ভুল দেখাবে
    
- reconciliation কঠিন হবে
    

কিন্তু system নিজে থেকে এটিকে `NoShow` বা `Consumed` বলবে না।

## Recommended lifecycle

```
Reserved
   │
   ├── Service Started → Consumed
   │
   ├── Cancelled → Released
   │
   ├── Rescheduled → Reservation transferred/updated
   │
   └── Long unresolved
           │
           └── UnresolvedExpired
```

আমি `UnresolvedExpired` নামটি `Abandoned`-এর চেয়ে বেশি নিরপেক্ষ মনে করি।

কারণ `Abandoned` শুনলে মনে হতে পারে patient booking abandon করেছে। কিন্তু আসলে system জানে না:

- patient এসেছিল কি না
    
- service হয়েছে কি না
    
- operator ভুলে গেছে কি না
    
- external system failure হয়েছে কি না
    

তাই:

```
QuotaReservationStatus = UnresolvedExpired
```

ভালো।

## Suggested fallback rule

উদাহরণস্বরূপ:

```
ScheduledDate + configurable resolution window
```

যেমন:

- scheduled date পার হলে pending review
    
- +1 business day: help desk queue
    
- +3 business days: supervisor escalation
    
- +30 বা +90 calendar days: automatic `UnresolvedExpired`
    

আমি সরাসরি 90 দিন hard-code করব না। বরং policy/configuration হিসেবে রাখব:

```
UnresolvedReservationExpiryDays
```

তবে V1 default হতে পারে:

```
90 days
```

### Important invariant

`UnresolvedExpired` হলে:

- quota future availability থেকে মুক্ত হবে
    
- historical ledger row মুছে যাবে না
    
- এটি `Consumed` নয়
    
- এটি `NoShow` নয়
    
- এটি `CancelledByPatient` নয়
    
- এটি financial reversal নিজে থেকে করবে না, যদি Invoice ইতিমধ্যে issued হয়ে থাকে

# 13. Claude-কে পাঠানোর জন্য final decision prompt

তুমি Claude-কে এভাবে বলতে পারো:

```text 

তোমার review-এর জন্য ধন্যবাদ। আমি redundancy concern গ্রহণ করছি, তবে CoverageSnapshot এবং CoverageDecisionAudit পুরোপুরি merge করছি না।

Final decision:

1. `BenefitEntitlement` V1-এ আলাদা persisted table হবে না। এটি resolver-এর domain/application-layer result হিসেবে থাকবে।
    
2. Successful confirmed booking-এর immutable resolved coverage context রাখার জন্য `HckScreeningCoverageSnapshot` থাকবে।
    
3. `HckCoverageDecisionAudit` আলাদা থাকবে, কারণ এটি meaningful decision attempts/history record করবে এবং একটি Screening-এর একাধিক audit row থাকতে পারে; Snapshot হবে confirmed booking প্রতি সর্বোচ্চ একটি final resolved record।
    
4. Snapshot এবং Audit-এর field-set identical হবে না:
    
    - Audit হবে decision-centric এবং lightweight।
        
    - Snapshot হবে confirmed booking-এর frozen coverage/package/financial/quota-basis context।
        
5. প্রতিটি technical resolver-call-এ audit row তৈরি হবে না। কেবল meaningful business decision attempt, denial, operator decision, self-pay override, বা materially changed resolution record হবে।
    
6. Invoice final financial source of truth থাকবে:
    
    - PayerType
        
    - TotalAmount
        
    - CorporatePayableAmount
        
    - PatientPayableAmount  
        Invoice final successful coverage snapshot-কে reference করতে পারে; arbitrary audit attempt-কে primary financial reference করা হবে না।
        
7. QuotaLedger-এ `Denied` status থাকবে না। এটি কেবল quota movement record করবে: Reserved, Consumed, Released, UnresolvedExpired।
    
8. `EffectiveTo` retroactively এমনভাবে পরিবর্তন করা যাবে না যাতে already-confirmed booking-এর historical resolved context invalid হয়ে যায়। Ordinary policy amendment হবে supersession-based।
    
9. Reserved quota চিরকাল আটকে থাকবে না। Escalation-এর পর configurable long timeout থাকবে; default হিসেবে 90 days বিবেচনা করা যায়। এরপর status হবে `UnresolvedExpired`—এটি NoShow বা Consumed নয়, তবে quota future availability-এর জন্য মুক্ত হবে এবং ledger history অক্ষত থাকবে।
    
```

এখন এই সিদ্ধান্ত অনুযায়ী updated conceptual model, entity responsibility, cardinality, FK direction, invariants এবং D19 update তৈরি করো। Schema/migration/code implementation শুরু করবে না যতক্ষণ না আমি design review approve করছি।
