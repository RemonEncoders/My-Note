আমি **Option 1** নেব।

কারণ এখানে শুধু FK target বদলাচ্ছেন না, **business meaning-ও বদলাচ্ছেন**।

আগে:

```text
PaymentMethodId
        │
        ▼
PaymentMethod (transaction entity)
```

এখন:

```text
PaymentTypeId
        │
        ▼
GeneralConfig (PaymentType)
```

এটা সম্পূর্ণ ভিন্ন concept।

## আমার recommendation

আমি Claude-কে বলতাম:

> **Option 1 নাও।**
> 
> `PharmacySale` এবং `PharmacyCustomerPayment`—দুটোতেই `PaymentMethodId/PaymentMethod` rename করে `PaymentTypeId/PaymentType` করো এবং FK `GeneralConfig`-এর `PaymentType` master-এ point করাও।
> 
> যেহেতু এখন business concept পরিবর্তন হয়েছে (transaction PaymentMethod থেকে master PaymentType), তাই property name-ও সেই অনুযায়ী পরিবর্তন হওয়া উচিত। ভবিষ্যতে domain model পরিষ্কার থাকবে এবং বিভ্রান্তি তৈরি হবে না।
> 
> একইসাথে ViewModel, DTO, Service, Validation, Repository, Mapping এবং Migration—সব জায়গায় consistent rename করো। কোনো compatibility alias বা পুরোনো naming রেখে দিও না, কারণ এই feature এখনো development-এ আছে এবং এখনই clean naming করার সবচেয়ে কম খরচের সময়।

### আমি আরেকটি ছোট বিষয় যোগ করব

যেহেতু এখন `PaymentType` একটি `GeneralConfig` reference, তাই property-টা এমন রাখাই ভালো:

```csharp
public Guid? PaymentTypeId { get; set; }

public GeneralConfig PaymentType { get; set; }
```

এবং validation হবে:

- Draft অবস্থায় `null` থাকতে পারে (যদি আপনার workflow তা অনুমতি দেয়)।
    
- Final/Confirm করার আগে `PaymentTypeId` অবশ্যই থাকতে হবে।
    
- Posting-এর সময় `IPaymentGlResolver.GetGlByPaymentTypeAsync(PaymentTypeId)` ব্যবহার করে GL resolve হবে।
    

এভাবে entity naming, business meaning এবং architecture—তিনটিই একসাথে সামঞ্জস্যপূর্ণ থাকবে।
