## Option 1 বাস্তবায়নের প্রস্তাব — শুধু বিদ্যমান HMS প্যাটার্ন

কোড ঘেঁটে যা পেলাম (গুরুত্বপূর্ণ context):

- এটা PHAR-এর সমস্যা নয়, **কোডবেস-ব্যাপী**: [InvoiceReceiveService.cs:373](vscode-webview://0tri44ar51et483btke71i178mqksugck1rce8n1q6b1u371eioe/HMS.Services/Areas/ACC/InvoiceReceiveService.cs#L373) — যেটাকে দেখে PHAR journal design করা হয়েছিল — হুবহু একই ত্রুটি বহন করে।

### প্রস্তাবিত ৩ অংশ

**A. Atomic status claim (DB-level)** — `ItemStockRepository.DecreaseQuantityAsync`-এর হুবহু প্যাটার্ন:

```csharp
Task<int> ClaimFinalAsync(Guid id);
//  .Where(x => x.Id == id && x.Status == Draft && !x.IsDeleted)
//  .ExecuteUpdateAsync(s => s.SetProperty(x => x.Status, Final)…)
```

0 rows ⇒ অন্য request আগেই দখল করেছে ⇒ `AlreadyUpdated`, কোনো side-effect নয়। Check-then-act নয়, একটাই atomic SQL — double-click/concurrent retry DB-লেভেলে বন্ধ। Sale ও Payment দুজায়গাতেই।

**B. Journal-কে একই transaction-এ আনা** — PHAR UoW-গুলোতে `JournalEntryRepository`/`JournalEntryItemRepository` (Sale-এর জন্য `JournalEntryTempRepository`) একই `_context` দিয়ে expose করা। তখন status + journal এক context, এক connection, এক transaction — একসাথে commit বা একসাথে rollback। এটা RFQService-এর নীতির প্রয়োগ, DbContext lifetime বা কোনো shared কোডে হাত পড়ে না। ৩০-সেকেন্ডের self-blocking-ও এতে চলে যায়।

⚠️ **একটা কথা আগেই জানানো দরকার:** HMS-এ কোনো UnitOfWork বর্তমানে অন্য area-র repository expose করে না। _মেকানিজম_ বিদ্যমান (একই `_context` দিয়ে repo তৈরি), কিন্তু cross-area _বিন্যাসটার_ HMS-এ নজির নেই। আপনার "নতুন প্যাটার্ন আবিষ্কার নয়" নির্দেশনার সীমারেখায় এটা পড়ে কিনা — সিদ্ধান্ত আপনার।

**C. DB-level journal duplicate guard (আপনার সিদ্ধান্ত দরকার)** — `acc_journal_entries(MaterialTransactionRecordId, FormCode)`-এ filtered unique index। যাচাই করেছি: বর্তমান DB-তে **কোনো duplicate নেই**, তাই index দেওয়া সম্ভব। কিন্তু এই টেবিল **সব module শেয়ার করে** — তাই এটা cross-module পরিবর্তন। প্রয়োজনে `WHERE FormCode IN (<PHAR codes>)` দিয়ে PHAR-এ সীমাবদ্ধ রাখা যায়। উল্লেখ্য, অংশ A নিজেই Pharmacy flow-এ duplicate অসম্ভব করে দেয় — C হলো অতিরিক্ত DB-level বেষ্টনী।

**Stock:** আপনার সিদ্ধান্ত মেনে পুরনো `IItemStockService`-এ কিছুই যোগ করব না। তবে অংশ A double-click-জনিত দ্বিগুণ stock deduction এমনিতেই ঠেকাবে। Phase 6-এ নতুন ledger PHAR UoW-এর context-এর উপর বানালে সে-ও স্বাভাবিকভাবেই এই transaction-এ ঢুকবে — একই ত্রুটির পুনরাবৃত্তি হবে না।
