`PharmacyCustomerPaymentGl`/`Invoice`-এর actual service usage আর multi-sale settlement workflow — দুটোই সরাসরি কোড থেকে যাচাই করেছি (আমার নিজের লেখা `PharmacyCustomerPaymentService.cs`সহ VC থেকে ট্রান্সফার করা `SalePharmacyController.GetBySupplierId`, `PharmacyCustomerInvoicePaymentModel.cs`)।

## প্রশ্ন ১: এক Payment কি একাধিক Sale invoice settle করতে পারবে?

**হ্যাঁ — এটা speculation না, ইতিমধ্যে data model ও controller-এ wired আছে।**

`SalePharmacyController.GetBySupplierId(Guid customerId)` (ইতিমধ্যে-ট্রান্সফার করা VC কোড) একটা নির্দিষ্ট customer-এর **সব outstanding (আংশিক/অপরিশোধিত) Sale invoice-এর তালিকা** রিটার্ন করে:

```csharp
foreach (var customerInvoiceItem in customerInvoiceList) {
    var paymentInvoiceItem = await model.GetPaymentCustomerInvoiceByIdAsync(customerInvoiceItem.Id);
    decimal totalInvoiceAmount = paymentInvoiceItem.Sum(x => x.InvoiceAmountPaid);
    decimal remainingAmount = customerInvoiceItem.InvoiceAmount - totalInvoiceAmount;
    if (remainingAmount >= 1) invoicePaymentItem.Add(customerInvoiceItem); // বাকি তালিকায় যোগ হয়
}
```

এটা একটা checklist তৈরির জন্য বানানো — cashier একাধিক Sale বেছে নিয়ে এক পেমেন্টে ভাগ করে দিতে পারবে। আর `GetPaymentCustomerInvoiceByIdAsync` real query চালিয়ে **প্রতিটা Sale-এর "কতটা এখনো পর্যন্ত পরিশোধ হয়েছে" গণনা করে `PharmacyCustomerPaymentInvoice.InvoiceAmountPaid` sum করে** — এবং এই sum একাধিক ভিন্ন Payment রেকর্ড জুড়েও হতে পারে (একই Sale-এ একাধিকবার আংশিক পেমেন্ট)। এটা pass-through storage না — এটা active, load-bearing calculation।

**উপসংহার: `PharmacyCustomerPaymentInvoice` genuinely প্রয়োজন — এটা বাদ দিলে "কোন Sale-এ কত বাকি" হিসাবটাই ভেঙে পড়বে।**

## প্রশ্ন ২: User কি journal post করার আগে ম্যানুয়ালি GL distribution edit করবে?

এখানেই আসল সমস্যা পেয়েছি। বর্তমান কোড (VC থেকে ট্রান্সফার করা `PharmacyCustomerAdvancePaymentModel`/`InvoicePaymentModel`) **manual GL-grid UI ধরে নিয়েছে**: `GlMasterList = await _glMasterService.GetAllGLMasterAsync();` — অর্থাৎ user একটা dropdown থেকে GL account বেছে debit/credit লাইন নিজে বানাবে, ঠিক SCM-এর AP মডিউলের মতো (যেখানে accountant staff কাজ করে)।

কিন্তু **এটা এই feature-এরই আগের সিদ্ধান্তের সাথে সরাসরি সাংঘর্ষিক**: আপনি নিজেই বলেছিলেন — "আমাদের Pharmacy Store-এর জন্য আলাদা Accountant... থাকবে না। Pharmacy Counter থেকেই Transaction Final হবে" এবং Patient Invoice-এর pattern অনুসরণ করতে চেয়েছেন। যাচাই করে দেখলাম **Patient Invoice-এর কোনো manual GL-grid নেই-ই** — সেটা GL account সরাসরি কোডে auto-compute করে (`_materialGLFindService.GetMaterialTransactionGlIdByCodeAsync` দিয়ে, hardcoded GL-code lookup, user কোনো dropdown থেকে কিছু বাছে না)।

**Service-এ `PharmacyCustomerPaymentGl`-এর actual ব্যবহার দেখলাম** (`PharmacyCustomerPaymentService.cs`):

- `AddAsync`/`UpdateAsync`: যা caller পাঠায় তাই raw save করে (কোনো validation না — debit=credit balance-ও চেক হয় না)
- `PostJournalAsync`: প্রতিটা row হুবহু `JournalEntryItem`-এ কপি হয়ে যায়, ১:১, কোনো computation/aggregation ছাড়া

অর্থাৎ **এটা pure pass-through — সার্ভিস নিজে কিছুই করে না, শুধু user যা দেয় তাই সংরক্ষণ ও কপি করে।**

## আমার সংশোধিত সুপারিশ

- **`PharmacyCustomerPaymentInvoice` — রাখুন।** Q1-এর উত্তর "হ্যাঁ" ও genuine, active ব্যবহার আছে।
- **`PharmacyCustomerPaymentGl` — সরিয়ে ফেলার সুপারিশ করছি।** Pharmacy counter staff-এর (কোনো accountant নেই) manual GL-account নির্বাচন করার কথা না — এটা বরং Patient Invoice-এর মতো **auto-computed GL distribution** হওয়া উচিত (posting-এর সময় সরাসরি নির্দিষ্ট GL code লুকআপ করে debit/credit বসানো, কোনো staging grid/entity ছাড়াই)। আমার আগের সুপারিশ ("existing pattern-এর সাথে মেলে তাই রাখুন") ভুল বিন্দু থেকে যুক্তি দিচ্ছিল — SCM-এর pattern মেলা মানেই সঠিক না, যেহেতু SCM-এ সত্যিকারের accountant থাকে, Pharmacy counter-এ থাকে না।

এটা একটা real design-simplification সুযোগ, শুধু "অন্য module-এও আছে তাই রাখতে হবে" এই যুক্তিতে না। আপনার সিদ্ধান্তের অপেক্ষায় আছি — `PharmacyCustomerPaymentGl` বাদ দিয়ে auto-computed GL posting-এ যাব, নাকি অন্য কোনো বিবেচনা আছে?
