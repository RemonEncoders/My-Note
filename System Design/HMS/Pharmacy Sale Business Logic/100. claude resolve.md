## 3. Transaction boundary `[CODE]` `[LIVE]`

```
tx-এর বাইরে (আগে):  ValidatePaymentModes → GetDefaultWarehouse → GenerateReqNo
── BeginTransaction ──
   header  (Add/Update + Complete)
   items   (Delete+Add + Complete)
   modes   (Delete + Complete, Add + Complete)
── Commit ── / catch → Rollback + throw
tx-এর বাইরে (পরে):   _productService.FindAllAsync
```

ভিতরে একাধিক `CompleteAsync()` আছে (child-দের header-এর Id দরকার) — কিন্তু সেগুলো একই DbContext-এর flush, atomicity transaction-ই দেয়। **`GenerateNumberService` অবশ্যই বাইরে**: এটি নিজের Transient `ApplicationDbContext` নিয়ে `phar_sales`-এ `COUNT(*)` চালায় — যে টেবিলে আমরা ভিতরে INSERT করছি; ভিতরে নিলে নিজের uncommitted row lock-এ নিজেই আটকে timeout হতো।

## 13. Remaining known limitations

- `[GAP]` **Due field-টি ব্রাউজারে JS দিয়ে গণনা হয়** (`calculateGrandTotal`)। এই session-এ Playwright শুধু CLI shim হিসেবে আছে, library হিসেবে নেই — তাই JS-চালিত মানটি ব্রাউজারে assert করা যায়নি। বদলে formula `[CODE]` পড়া হয়েছে এবং **server-side receivable boundary test** (ঠিক 100 pass, 100.01 block) দিয়ে server-এর নিজের arithmetic pin করা হয়েছে; harness JS-equivalent Due post করেছে এবং stored মান যাচাই হয়েছে।
- `[GAP]` **COGS/BSX journal লাইন আসেনি** — `GetGrUnitPriceByProductIdAndBatchNo` এই seeded batch-গুলোর জন্য 0 ফেরায় (কোনো GR নেই)। পূর্ব-বিদ্যমান আচরণ, split payment-এর সাথে সম্পর্কহীন।
- `[GAP]` **InvoiceDocNo generation racy** — `COUNT(*)`-ভিত্তিক, তাই একসাথে দুটি Add একই নম্বর পেতে পারে। পূর্ব-বিদ্যমান, এই কাজের scope-এ ছিল না।
- `[GAP]` `payment_type_gl_mappings`-এর **কোনো admin UI নেই**; unmapped payment type দিয়ে Confirm করলে (যেমন `Due / Credit`) journal post হবে না।
