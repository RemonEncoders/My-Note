এটা আসলে **Accounting Posting Lifecycle**-এর পার্থক্য। Claude জানতে চাইছে **Payment confirm হওয়ার পরে Journal কোথায় লেখা হবে?**

দুইটা প্যাটার্ন আছে।

# Pattern 1: Direct Posting (VitalityCash)

```
Customer Payment
       │
       ▼
Confirm
       │
       ▼
JournalEntry
JournalEntryItem
(Status = Posted)
```

এখানে Payment Confirm করার সাথে সাথে Journal **Permanent Ledger**-এ চলে যায়।

উদাহরণ:

রোগী ১০০০ টাকা Payment দিল।

```
Dr Cash          1000
    Cr Customer      1000
```

এই Entry সঙ্গে সঙ্গে JournalEntry টেবিলে Save হয়ে গেল।

এরপর Financial Report, Trial Balance, Ledger—সব জায়গায় এটা দেখা যাবে।

এখানে আর কোনো "Approve" ধাপ নেই।

# Pattern 2: Temporary Posting

```
Customer Payment
       │
       ▼
Confirm
       │
       ▼
JournalEntryTemp
(Status = Draft)
       │
Finance Review
       │
       ▼
Post
       │
       ▼
JournalEntry
(Status = Posted)
```

এখানে Confirm মানে Accounting শেষ না।

প্রথমে Draft Voucher তৈরি হয়।

Finance Manager Review করবে।

তারপর Permanent Journal-এ যাবে।

## তাই Claude আসলে কী জানতে চেয়েছিল?

সে এই প্রশ্নটাই করেছে:

> **HMS-এর Official Accounting Standard কোনটা?**

- Direct Posting?
    
- নাকি Draft → Post?
    

আপনার উত্তর অনুযায়ী,

> **Official Standard = Direct Posting**

তাহলে PharmacyCustomerPayment-ও Direct Posting করবে।

আর যদি PharmacySaleService এখনও `JournalEntryTemp` ব্যবহার করে, তাহলে সেটা সম্ভবত একটি **legacy বা incomplete implementation** যা পরে HMS-এর বর্তমান Accounting Pattern-এর সাথে Align করা উচিত।

আপনার আলোচনার ভিত্তিতে আমি যেটা বুঝলাম, আপনার Requirement হলো:

1. **HMS-এর Existing Accounting Pattern-ই Follow করতে হবে।**
2. **VitalityCash-এর Implementation অন্ধভাবে Copy করা যাবে না।**
3. **যদি HMS-এ Journal সরাসরি `JournalEntry`-তে Post হয়, তাহলে Pharmacy Customer Payment-ও একই Pattern Follow করবে।**
4. **একই PHAR Module-এর মধ্যে Sale এবং Payment-এর Journal Posting Mechanism Consistent হতে হবে।**



```txt title:"Claude-কে আমি এভাবে বলতাম:"
After reviewing the current HMS accounting architecture, I want the Pharmacy Customer Payment feature to follow the existing HMS journal posting pattern rather than the original VitalityCash implementation.

Please do not make the decision based on how VitalityCash works. Instead, verify the current HMS accounting flow and keep the Payment service consistent with it.

If the current HMS accounting module posts journals directly to `JournalEntry`/`JournalEntryItem`, then Pharmacy Customer Payment should do the same. There is no requirement to introduce a temporary or staged journal workflow for this feature.

Also, review the transferred `PharmacySaleService`. If it is still using a different journal posting mechanism than the current HMS accounting architecture, report that inconsistency before changing anything. I want the PHAR module to follow one consistent accounting pattern, not two different ones.

The guiding principle is:  
**HMS architecture is the source of truth. VitalityCash is only the source of business logic, not architectural decisions.**
```

এতে একটি গুরুত্বপূর্ণ নীতি স্পষ্ট হয়ে যাবে:

- **Business Logic** (payment calculation, invoice allocation, customer balance, GL account selection) → VitalityCash থেকে Adapt করা যাবে।
- **Architecture** (journal posting, Unit of Work pattern, DI pattern, accounting lifecycle) → **HMS যা Follow করছে সেটাই Follow করতে হবে।**

এতে ভবিষ্যতে Claude একই ভুল করবে না এবং HMS-এর প্রতিষ্ঠিত Architecture-কে অগ্রাধিকার দেবে।
