HMS-এর প্রকৃত accounting architecture যাচাই করেছি — ধারণা করিনি, সরাসরি কোড দেখেছি।

## যাচাই ফলাফল

HMS-এ আসলে **দুটো বৈধ, ইচ্ছাকৃত journal-posting মেকানিজম সহাবস্থান করছে** — কোনোটাই ভুল/অসামঞ্জস্যপূর্ণ না:

**১. Direct-to-permanent** (`JournalEntry`/`JournalEntryItem`, সরাসরি `Status = Posted`) — যেমন `InvoiceReceiveService.cs` (ACC মডিউল)-এ ব্যবহৃত।

**২. Temp staging → Promote** (`JournalEntryTemp`/`JournalEntryTempItem` → `IJournalEntryTempService.PromoteToPermanentAsync(tempId)` → তবেই permanent `JournalEntry`-তে যায়) — এটা **PharmacySaleService-এর নিজস্ব উদ্ভাবন না** — এটা ACC এরিয়ার নিজস্ব, পূর্ণাঙ্গ, dedicated subsystem (`HMS.Services/Areas/ACC/JournalEntryTempService.cs` + repository + controller + views সহ), এবং **IMS-এর `StockOutService`-ও একই মেকানিজম ব্যবহার করে**। অর্থাৎ এটা genuinely established HMS architecture-এর অংশ, PHAR-নির্দিষ্ট hack না।

**সিদ্ধান্ত**: `PharmacySaleService` এখানে **সঠিক, established pattern-ই অনুসরণ করছে** — কোনো inconsistency নেই যা রিপোর্ট করার দরকার। যেহেতু Payment-ও PHAR মডিউলেরই অংশ (Sale-এর মতোই), এবং Temp-staging pattern নিজেই genuine HMS architecture (শুধু VitalityCash-এর অনুকরণ না) — **`PharmacyCustomerPayment`-ও `JournalEntryTemp`/`PromoteToPermanentAsync` pattern অনুসরণ করবে**, যা PHAR মডিউলের অভ্যন্তরীণ সামঞ্জস্য বজায় রাখে এবং verified HMS convention-এর সাথেও মেলে।

এই সিদ্ধান্তে সম্মত হলে Phase 3 implementation শুরু করছি (repository layer + 706-line service adapt, CompanyId/ActivityLog বাদ দিয়ে, Temp-journal pattern দিয়ে)।

_(এবং, `/compact` কমান্ড সম্পর্কে — এটা CLI-এর built-in context-compaction ফিচার, আমার নিজের কোনো টুল দিয়ে চালানোর কিছু না; harness নিজে থেকেই এটা হ্যান্ডল করবে, আমি স্বাভাবিকভাবে কাজ চালিয়ে যাচ্ছি।)_
