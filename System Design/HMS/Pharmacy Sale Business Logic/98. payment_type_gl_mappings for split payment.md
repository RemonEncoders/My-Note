এই GL mapping বিষয়টাকে এখন ignore করো না। Split-payment-এর Confirm বাস্তবে কাজ করার জন্য এটা একটি mandatory dependency।

তবে এখনই নিজের মতো করে admin screen বানানো শুরু করবে না।

### প্রথমে যা করবে

`payment_type_gl_mappings` পুরোপুরি analyze করো:

1. Entity
    
2. Repository / Service
    
3. Existing seed data আছে কি না
    
4. Migration history
    
5. `IPaymentGlResolver` কীভাবে mapping খোঁজে
    
6. কোন `PaymentTypeId` ব্যবহার হচ্ছে
    
7. অন্য কোনো module (বিশেষ করে existing PHAR Customer Payment / Payment module) এই mapping কীভাবে expected বলে ধরে
    
8. কোনো existing configuration/admin UI বা seeder pattern আছে কি না
    

বিশেষভাবে verify করো:

**PaymentType master → PaymentTypeId → payment_type_gl_mappings → GL Account → Journal Debit**

এই পুরো chain।

### তারপর আমাকে report করবে

- বর্তমানে mapping table কেন empty
    
- এটা pre-existing সমস্যা নাকি এই split-payment implementation-এর কারণে
    
- existing architecture অনুযায়ী mapping কোথায় maintain করার কথা
    
- minimum safe solution কী
    
- Admin screen দরকার কিনা
    
- নাকি শুধু proper seed/configuration যথেষ্ট
    

### গুরুত্বপূর্ণ

Split-payment implementation-এর E2E verification এখনই "pass" বলবে না যদি mapping না থাকার কারণে Confirm পর্যন্ত যাওয়া না যায়।

আমার কাছে দুইটি জিনিস আলাদা:

**Feature implementation**

- Multiple payment method UI
    
- PaymentMode persistence
    
- Validation
    
- Journal N debit lines
    
- Partial payment
    
- Transaction
    
- Backward compatibility
    

**Environment prerequisite**

- `payment_type_gl_mappings`-এ valid PaymentType → GL mapping থাকা
    

তাই report-এ এটাকে `[GAP] / ENVIRONMENT PREREQUISITE` হিসেবে clearly দেখাবে।
