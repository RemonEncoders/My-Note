তাহলে **একটা `PaymentModeId` header-এ রাখা আর সম্ভব না।** কারণ header-এ একটাই PaymentMode রাখা যায়, কিন্তু আপনার requirement অনুযায়ী এক payment-এ একাধিক mode থাকবে।

### আমি কী সিদ্ধান্ত নিতাম

আমি `PharmacyCustomerPaymentMode` নামে child entity-টাই রাখতাম।

কিন্তু **Header Amount আমি বাদ দিতাম না।** কারণ Hospital Billing-এ সাধারণত Header Amount রাখা হয় audit, reporting এবং UI-এর জন্য।

উদাহরণ:

Customer-এর Due = **৳1000**

Customer payment:

|Payment Mode|Amount|
|---|--:|
|Cash|৳300|
|Card|৳500|
|Mobile Banking|৳200|

Header

```
TotalAmount = 1000
```

Child

```
Cash     = 300
Card     = 500
Mobile   = 200
```

Backend validation

```
TotalAmount == Sum(PaymentModes.Amount)

1000 == 300+500+200
```

যদি না মিলে

```
BusinessRuleException
```

এটা derive করলেও চলবে, কিন্তু Header Amount রাখলে UI, Report, Search, Grid, Audit—সব সহজ হয়।

### ReferenceNo

Header-এর ReferenceNo আমি রাখতাম না।

কারণ Cash-এর reference লাগে না।

Card-এর POS Transaction ID লাগে।

Bank-এর Cheque No লাগে।

Mobile Banking-এর TxnId লাগে।

অর্থাৎ Reference mode-specific।

তাই

```
PaymentMode
------------
Cash
Amount=300
ReferenceNo=NULL

Card
Amount=500
ReferenceNo=POS12345

Mobile Banking
Amount=200
ReferenceNo=TXN88991
```

এটাই সঠিক ডিজাইন।

### Pharmacy Sale-এর কী হবে?

এখানে আমি **এখনই split payment যোগ করতাম না**।

কারণ এটা scope অনেক বাড়িয়ে দেবে।

বর্তমান flow:

```
Sale
   ↓
PaymentType
   ↓
Journal
```

নতুন flow হবে

```
Sale
   ↓
SalePaymentModes
   ↓
Multiple GL
   ↓
Journal
```

মানে Sale-এর View, Entity, Service, Validation, Posting—সব পরিবর্তন করতে হবে।

যেহেতু আপনার প্রশ্ন ছিল **Customer Payment** নিয়ে, তাই PharmacySale আপাতত single payment mode থাকুক।

পরে যদি business বলে

> "Sale create করার সময়ও Cash + Card নেওয়া যাবে"

তখন একই `PaymentMode` pattern Sale-এও reuse করবেন।

### আমি Claude-কে যা বলতাম

Requirement update confirmed.

We need to support **split payment** (Cash + Card + Mobile Banking, etc.) within a single `PharmacyCustomerPayment`. Therefore, a single header-level `PaymentTypeId/PaymentModeId` is no longer sufficient.

Please implement a child collection (`PharmacyCustomerPaymentMode`) where each row contains:

- PaymentTypeId (GeneralConfig)
    
- Amount
    
- ReferenceNo (optional, mode-specific)
    

Please keep `Header.TotalAmount` as the declared payment amount and validate:

`Header.TotalAmount == Sum(PaymentModes.Amount)`

Do **not** keep a single header-level `ReferenceNo`; reference information should belong to each payment mode because Card, Bank, Cheque, Mobile Banking, etc. have different reference values.

Journal posting should generate:

- One Debit entry for each payment mode (resolved through `PaymentTypeGlMapping`)
    
- One Credit entry to the customer's Receivable/Advance GL for the total amount
    

For now, **apply this design only to PharmacyCustomerPayment**. **Do not change PharmacySale** to support split payment in this phase. We will keep PharmacySale as a single payment mode unless the business explicitly requires split payment there in a future enhancement.

এই সিদ্ধান্তটা future-proofও। পরে যদি Pharmacy Sale-তেও multiple payment support লাগে, একই `PaymentMode` child pattern reuse করতে পারবেন—নতুন architecture বানাতে হবে না।
