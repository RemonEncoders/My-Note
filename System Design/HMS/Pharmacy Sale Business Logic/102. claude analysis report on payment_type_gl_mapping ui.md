# PRIORITY 3 — `InvoiceDocNo` COUNT(*) race

**১. বর্তমান implementation — দুটো একই রকম COUNT-ভিত্তিক:**

```csharp
// GenerateNumberService.cs:22-27  (AddAsync এটাই ব্যবহার করে)
int count = await Set<TEntity>().CountAsync(x => x.Created.Year == DateTime.Now.Year);
return yy + formCode("00") + (count+1)("00000");     // 26 18 00012

// PharmacySaleRepository.cs:58-61 — হুবহু ডুপ্লিকেট
```

**২/৩. ঝুঁকি:** দুটো concurrent Add একই count পড়ে → **একই InvoiceDocNo**, আর `phar_sales`-এ **`InvoiceDocNo`-তে কোনো unique index নেই** (index list: PK + ৫টা FK index মাত্র) → নীরবে duplicate invoice নম্বর DB-তে বসে যাবে। Invoice payment allocation ও print দুটোই নম্বরের উপর নির্ভরশীল।

**৪. Pre-existing?** **সম্পূর্ণ pre-existing** — `GenerateNumberService<TEntity>` generic, ~২০টা service ব্যবহার করে (Registration, PO, IR, Employee…)। Split payment এটা ছোঁয়নি এবং খারাপও করেনি (Add-এ ১টাই sale row তৈরি হয়, আগেও তাই ছিল)।

**৫. Evidence:** উপরের কোড; `sys.indexes` query-তে `InvoiceDocNo` অনুপস্থিত; dev DB-তে এখন duplicate নেই (মাত্র ~১২টা sale, single-user)। পাশাপাশি একটা pre-existing অদ্ভুততা: Confirm-এ `JournalEntryTempNo`-ও `IGenerateNumberService<PharmacySale>` দিয়ে তৈরি হয় — অর্থাৎ **journal নম্বর sale count থেকে আসে**। আমার কাজের অংশ নয়, জানিয়ে রাখলাম।

**৬. Minimum-risk solution (format অপরিবর্তিত):**

- **নতুন table `sys_document_sequences (FormCode, Year, LastNumber)`** + atomic `UPDATE … SET LastNumber = LastNumber + 1 … OUTPUT inserted.LastNumber` (এক statement, row lock — race নেই)। `yy+code+00000` format হুবহু একই থাকে।
- **সাথে filtered unique index `phar_sales.InvoiceDocNo`** — backstop।
- ⚠️ **shared `GenerateNumberService<TEntity>` বদলাব না** — ২০টা module-এ ঝুঁকি। PHAR-এর জন্য আলাদা allocation path (repository-র নিজস্ব method) ব্যবহার করব; পরে অন্য module ইচ্ছে করলে migrate করবে।

**৭. ফাইল:** নতুন entity + repository + `PharmacySaleRepository.GenerateReqNoAsync` rewrite + `PharmacySaleService.AddAsync`-এর call। **৮. Migration:** হ্যাঁ — ১টা (নতুন table + unique index)। **তার আগে বিদ্যমান duplicate আছে কিনা যাচাই করতে হবে** (এখন নেই)। **৯. Regression:** PHAR sale নম্বরিং; অন্য module অস্পৃষ্ট। **১০. টেস্ট:** ১০টা concurrent Add → ১০টা ভিন্ন নম্বর, format অপরিবর্তিত; unique index থাকা অবস্থায় ইচ্ছাকৃত duplicate → DB reject। **১১. যা বদলাবে না:** দৃশ্যমান format, অন্য module-এর নম্বরিং।

**২. ব্যবসায়িক ঝুঁকি:** receivable manipulation। **৩. কারিগরি ঝুঁকি:** কম — server-এ হিসাবের সব উপাদান আছে।

**৬. Minimum-risk solution:** server ইতিমধ্যেই হিসাব করতে পারে — `CalculateReceivableAmount(entity)` [PharmacySaleService.cs:531-538](vscode-webview://0tri44ar51et483btke71i178mqksugck1rce8n1q6b1u371eioe/HMS.Services/Areas/PHAR/PharmacySaleService.cs#L531-L538) আছে।

- `AddAsync`/`UpdateAsync`-এ posted মান copy না করে **server-এ recompute**: `InvoiceAmount = CalculateReceivableAmount(entity) − PaidAmount`
- `TotalPrice`-ও একই সাথে recompute (এখন post-ই হয় না, null বসছে)
- দুই view থেকে `name="InvoiceAmount"` সরিয়ে `id` রাখা → JS live display অটুট, কিন্তু আর post হয় না
- **কলামগুলো persisted-ই থাকবে** — `GetBySupplierId` snapshot হিসেবে এর উপর নির্ভরশীল

|ক্ষেত্র|পরিণতি|
|---|---|
|`PaidAmount`|persisted, **server-derived** (ইতিমধ্যে)|
|`InvoiceAmount` (Due)|persisted, **server-derived হবে** ← পরিবর্তন|
|`TotalPrice`|persisted, **server-derived হবে** ← পরিবর্তন|
|line `TotalPrice`/`NetPrice`/`VatValue`|এখনো browser থেকে — **আলাদা, বড় hardening**; আজ সুপারিশ করছি না|

**৭. ফাইল:** `PharmacySaleService.AddAsync`/`UpdateAsync`; `Add.cshtml` + `Edit.cshtml` (শুধু `name` সরানো)। **৮. Migration:** নেই। **৯. Regression:** Due-র মান বদলাতে পারে যদি browser আর server ভিন্ন হিসাব করে — **তাই আগে বিদ্যমান sale-এ দুই হিসাব মিলিয়ে দেখব**। `AdvanceAmount` (সবসময় 0, কোনো UI নেই) এখানে বাদ, memory §153-এর সতর্কতা অনুযায়ী। **১০. টেস্ট:** curl-এ বানানো `InvoiceAmount=0` পাঠিয়ে দেখা যে server নিজেরটা লেখে; discount সহ/ছাড়া partial payment-এ Due সঠিক; `GetBySupplierId` ঠিক বাকিটা দেখায়। **১১. যা বদলাবে না:** partial payment, overpayment guard, `Sum(modes)==PaidAmount`, journal।
