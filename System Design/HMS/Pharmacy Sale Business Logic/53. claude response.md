বিশ্লেষণ শেষ — কোনো কোড পরিবর্তন করিনি।

## ১. Payment Method dropdown — একই data source reuse করা যাচ্ছে কি?

**হ্যাঁ, ইতিমধ্যে হয়ে গেছে।** দুটো Payment web model-ই (`PharmacyCustomerAdvancePaymentModel`, `PharmacyCustomerInvoicePaymentModel`) `PharmacySaleModel`-এর সাথে **হুবহু একই কল** ব্যবহার করে:

```cs
PaymentMethodList = new SelectList(await _paymentMethodService.GetPaymentMethodListAsync(), "Id", "Name");
```

একই `IPaymentMethodService`, একই `SelectList("Id","Name")` shape — নতুন কোনো lookup logic লেখা হয়নি। Entity-level ফিল্ডও একই টাইপ: `PharmacySale.PaymentMethodId`/`PharmacyCustomerPayment.PaymentMethodId` দুটোই `Guid?` → `HMS.Entities.Areas.ACARE.PaymentMethod`।

**Validation** এখন service-স্তরে হয় (`PostJournalAsync`-এ `PaymentMethodId == null` হলে `BusinessRuleException`) — Draft অবস্থায় বাধ্যতামূলক না, কিন্তু Final করার আগে অবশ্যই লাগবে। View তৈরির সময় ঠিক করতে হবে: Add form-এই required করে দেব, নাকি Draft-এ optional রেখে শুধু Final-এর সময় আটকাবো (এই ছোট UX সিদ্ধান্তটা Phase 4-এর ভিউ বানানোর সময় নেওয়া দরকার)।

## ২. PaymentMethodId কোথায় থাকবে — একবারই নির্বাচন?

**গঠনগতভাবেই নিশ্চিত — Gl grid বাদ দেওয়ার ফলে এটা এমনিতেই একবার-নির্বাচনযোগ্য হয়ে গেছে।** `PaymentMethodId` এখন `PharmacyCustomerPayment` header entity-র একটা single scalar ফিল্ড (আগে Gl grid-এর প্রতিটা লাইনে আলাদা DcType থাকতে পারত, কিন্তু সেই grid-ই নেই এখন)। দুটো payment-type (Advance/Invoice) মডেলই সরাসরি এই একই header entity extend করে — তাই UX-এ এটা Customer, PaymentDate, Amount, Currency-র পাশে **header-level একটা dropdown** হিসেবে থাকবে, `CustomerInvoicePaymentItemList`/`CustomerAdvancePaymentItemList` (multi-sale allocation grid) থেকে সম্পূর্ণ আলাদা — grid-এর প্রতিটা row-এ repeat হবে না।

## ৩. Hidden dependency যাচাই

পুরো solution জুড়ে grep করে দেখলাম — **`PharmacyCustomerPaymentGl`/`IPharmacyCustomerPaymentGlRepository`/`PharmacyCustomerPaymentGlRepository`-এর কোনো অবশিষ্ট রেফারেন্স নেই কোথাও** (0 files)। Controller-এর `GetCustomerPaymentEntryGlByCustomerId` JSON action এখনো ঠিকভাবে কাজ করে — এটা কখনোই removed Gl entity-র ওপর নির্ভর করেনি, শুধু `CustomerVendor.ReconGlId`/`AdvanceGlId` lookup করে (GL preview দেখানোর জন্য এখনো useful থাকতে পারে)। JavaScript এখনো লেখা হয়নি (Views-ই বাকি), তাই সেখানে ভাঙার মতো কিছু নেই। **কোনো hidden dependency পাওয়া যায়নি।**

## ৪. Patient Invoice UX থেকে কী reuse করা যাবে

চেক করে দেখলাম — **SCM-এর `VendorCustomerPayment`/`AdvancePaymentEntry`-র (Pharmacy Payment-এর সবচেয়ে কাছাকাছি sibling, একই multi-invoice-allocation দরকার) কোনো View-ই তৈরি হয়নি এখনো** (Controller পর্যন্ত নেই) — অর্থাৎ "একাধিক outstanding invoice checkbox দিয়ে বেছে payment ভাগ করা"-র জন্য copy করার মতো কোনো existing View নেই এই কোডবেসে।

ACARE-এর Patient Invoice (`Add.cshtml` + `_CashPayment`/`_BankPayment`/`_CardPayment`/`_DuePayment`/`_EWalletPayment` partials) সত্যিই তৈরি আছে, কিন্তু কাঠামোগতভাবে **ভিন্ন মডেল** — সেখানে এক Invoice-এ **একই সাথে একাধিক payment method** (Cash+Card+Bank ইত্যাদি একসাথে) split করা যায় (৫টা আলাদা child entity দিয়ে), Pharmacy-র মতো single dropdown-ভিত্তিক না। যেহেতু আমরা Pharmacy-তে `PharmacySale`-এর simple single-`PaymentMethodId` pattern অনুসরণ করছি, ACARE-এর এই জটিল multi-method-split UI copy করা উপযুক্ত না — বরং **PharmacySale নিজের Add screen-এর pattern-ই Pharmacy Payment-এর জন্য সবচেয়ে সরাসরি, সামঞ্জস্যপূর্ণ reference** (দুটোই একই PHAR module, একই simple dropdown shape)।

**সংক্ষেপে reuse-করণীয়**: `IPaymentMethodService` dropdown pattern (PharmacySale থেকে, ইতিমধ্যে করা হয়েছে) + সাধারণ card/layout CSS convention (ACARE-এর `inv-add-card` স্টাইল ক্লাসগুলো generic, চাইলে visual consistency-র জন্য নেওয়া যায়)। কিন্তু "multi-invoice checklist" ও "multi-method split payment" — দুটোর কোনোটাই কোথাও তৈরি নেই, Phase 4-এ নতুন করেই বানাতে হবে, তবে **কোনো নতুন design প্যাটার্ন উদ্ভাবন না করে** — PharmacySale-এর নিজস্ব ইতিমধ্যে-approved GetBySupplierId ডেটা-শেপ অনুসরণ করেই।
