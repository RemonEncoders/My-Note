## Verification রিপোর্ট (Phase 5-এর আগে)

Read-only যাচাই শেষ হয়েছে। বেশিরভাগ চেকলিস্ট আইটেম পরিষ্কার পাওয়া গেছে, কিন্তু **দুটো গুরুত্বপূর্ণ, empirically-প্রমাণিত architectural defect পাওয়া গেছে** — আপনার নির্দেশ অনুযায়ী **কোনো ফিক্স না করেই থামছি এবং রিপোর্ট করছি।**

### ✅ পরিষ্কার (কোনো সমস্যা নেই)

- **PaymentMode child rows**: Add/Update/Delete সঠিকভাবে কাজ করছে — live test করে দেখা গেছে edit করলে পুরনো row সত্যিই DB থেকে মুছে যায় (হার্ড ডিলিট), কোনো orphan row থাকে না, নতুন TotalAmount সঠিকভাবে match করে।
- **Migration ও schema sync**: `dotnet ef migrations has-pending-model-changes` → "কোনো pending change নেই।" সম্পূর্ণ synchronized।
- **Split payment-এর গণিত**: `ValidatePaymentModes` gate-এর কারণে Debit-দের যোগফল সবসময় Credit-এর সমান হয় (decimal arithmetic, কোনো rounding ঝুঁকি নেই) — **কিন্তু** এটা তখনই কাজে আসে যদি journal আদৌ তৈরি হয় (নিচে দেখুন কেন সবসময় হয় না)।
- **Partial/Full payment balance logic**: কাঠামোগতভাবে সঠিক, তবে একটা hidden ঝুঁকি নোট করেছি — `AdvanceAmount` ফিল্ডের জন্য কোনো UI নেই বলেই বর্তমানে দুটো আলাদা জায়গায় (GetBySupplierId vs Details/Print) স্বাধীনভাবে গণনা করা "due amount" সূত্র মিলে যাচ্ছে; ভবিষ্যতে `AdvanceAmount` UI যোগ হলে এই দুটো সূত্র নিঃশব্দে ভিন্ন ফলাফল দিতে পারে।

### ❌ গুরুত্বপূর্ণ সমস্যা: Journal posting একই সাথে **atomic নয়** এবং **idempotent নয়**

এটা **Sale এবং Payment দুটোতেই** একই প্যাটার্নে আছে (`PharmacySaleService.UpdateStatusAsync` ও `PharmacyCustomerPaymentService`-এর status method গুলো) — এই সেশনে নতুন তৈরি bug নয়, বরং Phase 2/3 থেকেই বিদ্যমান একটা systemic gap।

**১. Non-atomic commit (লাইভ টেস্টে reproduce করা হয়েছে):** status update ও journal posting আলাদা `SaveChanges()` কলে হয়, কোনো transaction দিয়ে wrap করা নেই। আমি একটা Draft payment-এ `UpdateStatus` কল করেছি যার customer-এর `AdvanceGlId` কনফিগার করা ছিল না — ফলাফল: **status সত্যিই "Final" হয়ে গেছে DB-তে, কিন্তু journal entry শূন্য (0)।** এটা একটা বাস্তবসম্মত ও সহজে ঘটতে পারা data-gap (customer-এর GL কনফিগার না থাকা), যা silently একটা "confirmed" payment তৈরি করে যার কোনো accounting trail নেই।

**২. কোনো idempotency guard নেই:** `PharmacyCustomerPaymentService`-এর status method গুলো প্রতিবার (Final অবস্থায় থাকা সত্ত্বেও) নিঃশর্তভাবে `PostJournalAsync` কল করে — double-click বা retry হলে duplicate journal posting হবে। `PharmacySaleService`-এ একটা "AlreadyUpdated" message flag আছে বটে, কিন্তু সেটা শুধু UI message-এর জন্য — stock deduction ও journal posting কোড তার নিচে **নিঃশর্তভাবে** চলে, তাই দ্বিতীয়বার call করলে stock-ও দ্বিতীয়বার কমবে!

**সরাসরি উত্তর আপনার প্রশ্নের**: "Journal entries created exactly once per confirmed transaction" — **এই গ্যারান্টি এখন নেই** (শূন্যও হতে পারে, একাধিকও হতে পারে, timing/retry-এর উপর নির্ভর করে)।

### প্রস্তাবিত সমাধান (এখনো implement করিনি)

- Status-update + journal-posting একটা single DB transaction-এ wrap করা (failure হলে rollback হবে)
- Side-effect (stock/journal) চালানোর আগে `if (entity.Status == Final) return;` ধরনের early-exit guard যোগ করা

দুটোই দরকার হতে পারে, শুধু একটা যথেষ্ট নয়। যেহেতু Sale ও Payment দুটোতেই একই shape-এর সমস্যা, ফিক্সের প্যাটার্নও দুটোতে consistent রাখা উচিত।
