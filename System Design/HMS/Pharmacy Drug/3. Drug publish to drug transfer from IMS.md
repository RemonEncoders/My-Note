## Final Architecture

### 1. Product becomes the Enterprise Master

`Product` will become the single enterprise master for every inventory item in the ERP.

It must support not only Pharmacy but also future modules such as:

- Pharmacy
    
- Laboratory
    
- OT
    
- CSSD
    
- Blood Bank
    
- Kitchen
    
- General Store
    
- Medical Equipment
    

Every inventory-related module will reference the same Product.

---

### 2. Drug becomes a Pharmacy Extension

`Drug` is no longer the master inventory entity.

Instead, Drug becomes a module-specific extension of Product.

Relationship:

Product (Parent)  
↓  
Drug (Child)

Drug will contain only pharmacy-specific information.

---

### 3. Remove the Publish Architecture

The current workflow is:

Drug  
↓  
Publish  
↓  
Product

This architecture will be removed.

Instead, Drug Registration itself becomes the controlled entry point.

When a Pharmacy user creates a Drug:

- Create Product
    
- Create Drug
    
- Link Drug.ProductId
    

Everything must happen inside one database transaction.

There will be no Publish button anymore.

ProductPublisher and PublishedProductLink should become obsolete after migration.

---

### 4. Data Ownership

Product owns:

- Product Code
    
- Product Name
    
- Category
    
- Inventory Measurement Unit (Normalized UOM)
    
- Inventory master information
    

Drug owns:

- Generic
    
- Brand
    
- Strength
    
- Form
    
- Dispensing UOM
    
- Default Conversion Factor
    
- Selling Price / MRP
    
- Safety flags
    
- Pharmacy-specific information
    

No duplicated master data should exist between Product and Drug.

---

### 5. Inventory Flow

SCM always works using:

Product.MeasurementUnit

PO  
→ GRN  
→ ItemStock  
→ Inventory Transfer  
→ Stock Ledger

must all use Product.MeasurementUnit.

---

### 6. Pharmacy Flow

Pharmacy Receipt loads:

- Product.MeasurementUnit
    
- Drug.DispensingUOM
    
- Drug.DefaultConversionFactor
    

Receiver may override the conversion factor before confirming receipt.

The overridden value must be stored in the receipt document for audit purposes.

Only after receipt confirmation should PharmacyItemStock be increased.

Pharmacy stock is always stored using Dispensing UOM.

Pharmacy Sale always deducts stock using Dispensing UOM.

## FINAL BUSINESS REQUIREMENT

During Pharmacy Sale, the system must automatically suggest which PharmacyItemStock batch/cost layer should be used.

### 1. Default batch-selection priority

The system's default recommendation must follow this priority:

Priority 1 — FEFO

- Select/suggest the stock layer with the earliest expiry date first.
    

Priority 2 — Lower Unit Cost

- If multiple eligible stock layers have the same expiry priority, prefer the lower recorded purchase/unit cost.
    

Therefore:

FEFO is the FIRST priority.  
Lower Unit Cost is the SECOND priority.

This is the system's DEFAULT recommendation/allocation strategy.

### 2. Seller MUST be able to override the suggested batch

The FEFO + lower-cost rule must NOT be an absolute restriction.

The Pharmacy Seller intentionally may choose another available batch.

Example:

System suggests:

- Batch B002
    
- Expiry: 2026-09-30
    
- Unit Cost: ৳18
    

But seller intentionally chooses:

- Batch B003
    
- Expiry: 2027-03-30
    
- Unit Cost: ৳15
    

This must be allowed, provided the selected batch/cost layer has sufficient available quantity and satisfies normal stock-validation rules.

The system must NOT silently replace the seller's selected batch with the FEFO batch.

### 3. COGS must follow the ACTUAL selected batch/cost layer

This is critical.

If the system suggests B002 but the seller overrides and selects B003:

- Stock must decrease from B003.
    
- COGS must use B003's recorded unit cost.
    
- The system must NEVER use B002's cost while decreasing B003's quantity.
    

Formula:

COGS = Sold Dispensing Quantity × Selected Stock Layer Unit Cost

Example:

B002:  
100 Tablet @ ৳18

B003:  
300 Tablet @ ৳15

Seller sells:  
50 Tablet

System suggests B002, but seller manually selects B003.

Then:

Stock decrease:  
B003: 300 → 250 Tablet

COGS:  
50 × ৳15 = ৳750

NOT:  
50 × ৳18 = ৳900

### 4. Batch and cost layer are both important

Do not assume that BatchNo alone uniquely identifies a cost layer.

The same BatchNo may exist in multiple PharmacyItemStock records when the purchase/unit cost is different.

Example:

Record A:  
Batch = B001  
Expiry = 2026-12-31  
Quantity = 500 Tablet  
Unit Cost = ৳20

Record B:  
Batch = B001  
Expiry = 2026-12-31  
Quantity = 100 Tablet  
Unit Cost = ৳25

These must remain separate stock/cost layers.

Do NOT merge them merely because BatchNo is identical.

If a sale consumes Record A, decrease Record A.  
If it consumes Record B, decrease Record B.

### 5. Conversion and dispensing-unit context

The PharmacyItemStock quantity and unit cost are already expected to be normalized into the Pharmacy dispensing unit during the Pharmacy Receipt confirmation process.

For example:

Source:  
10 Box

Conversion Factor:  
1 Box = 50 Tablet

Purchase/Source Unit Cost:  
৳1,000 / Box

After Pharmacy Receipt confirmation:

Pharmacy stock:  
Quantity = 500 Tablet

Normalized Unit Cost:  
৳1,000 ÷ 50 = ৳20 / Tablet

Total inventory value remains unchanged:

10 × ৳1,000 = 500 × ৳20 = ৳10,000

Therefore Pharmacy Sale must work entirely with the normalized dispensing-unit quantity and normalized unit cost stored in PharmacyItemStock.

Do NOT go back to GoodsReceive during every sale just to recalculate the cost if the PharmacyItemStock already contains the authoritative cost layer.
