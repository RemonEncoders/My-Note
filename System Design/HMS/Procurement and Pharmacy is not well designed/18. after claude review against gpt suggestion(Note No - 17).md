সঠিক — এবং এটা আসলে আপনার কোডবেসের নিজস্ব দর্শনের সাথেই বেশি সামঞ্জস্যপূর্ণ। `AuditableEntity` কনভেনশনটাই তো ঠিক এই নীতির উপর দাঁড়িয়ে — **প্রতিটা অ্যাগ্রিগেট নিজের `Created`/`CreatedBy` নিজে বহন করে**, কোনো কেন্দ্রীয়/শেয়ার্ড audit-log টেবিলের উপর নির্ভর করে না। আপনি যা বলছেন তা এই একই নীতির সম্প্রসারণ মাত্র — Drug নিজের lifecycle প্রশ্নের উত্তর নিজেই দিতে পারবে, কোনো external join ছাড়াই।

আরেকটা কোণ থেকে দেখলে এটা আসলে DRY ভঙ্গ করছেও না — `Drug.PublishedAt` আর `PublishedProductLink.Created` **ভিন্ন প্রশ্নের উত্তর দেয়**, যদিও মূল্য একই মুহূর্তে সেট হয়:

- `Drug.PublishedAt` = "এই ব্যবসায়িক সত্তা কবে Published state-এ ঢুকেছিল?" (domain question)
- `PublishedProductLink.Created` = "এই integration mapping কবে তৈরি হয়েছিল?" (infrastructure question — যেমন কখনো re-sync/migration হলে link পুনর্নির্মিত হতে পারে, তখন এই দুটো ভ্যালু ভিন্ন হয়ে যেতেই পারে)

তাই দুটো ভিন্ন উদ্দেশ্যে দুটো জায়গায় থাকাটাই সঠিক, ডুপ্লিকেশন না।

## চূড়ান্ত, একত্রিত ডিজাইন

```
Drug (AuditableEntity)
    ...(clinical ফিল্ড)...
    ProductId        Guid?
    PublishedAt      DateTime?
    PublishedBy      Guid?
    DiscontinuedAt   DateTime?
    DiscontinuedBy   Guid?

PublishedProductLink (AuditableEntity)  — neutral, root-level, generic
    ProductId        Guid    (unique)
    SourceModule     string  (e.g. "PHAR.Drug")
    SourceEntityId   Guid    (e.g. Drug.Id)
    unique index: (SourceModule, SourceEntityId)

Product — অপরিবর্তিত, কোনো নতুন ফিল্ড না
```

**দায়িত্ব বণ্টন** (আপনার লাইনেই):

- **Drug** → নিজের lifecycle ও audit-এর মালিক।
- **PublishedProductLink** → cross-module identity mapping-এর মালিক (SCM-এর Edit UI শুধু এই টেবিলে রো আছে কিনা চেক করবে, read-only lock করার জন্য)।
- **Product** → বিশুদ্ধ procurement/inventory entity, কোনো integration metadata বহন করে না।

চারটা প্রশ্নই এখন resolved। আমি এখন পুরো আর্কিটেকচারটা (Published Product Pattern নাম, ডায়াগ্রাম, ৩-state derived lifecycle, transaction boundary, field-mapping টেবিল, ownership নিয়ম — সবকিছু) `docs/PHAR-SCM-Integration-Design.md`-এ লিখে ফেলছি রেফারেন্সের জন্য।

# PHAR ↔ SCM/IMS Integration — the Published Product Pattern

Status: **design locked — not yet implemented** (branch `feat/834-pharmacy-module`).
Companion to [PHAR-Drug-Master-Design.md](PHAR-Drug-Master-Design.md) and [modules/PHAR.md](modules/PHAR.md).
This document is the authoritative reference for how PHAR's `Drug` participates in the existing
SCM/IMS procurement pipeline (`Purchase Request → Purchase Order → Goods Receive → Inventory
Transfer`) without merging, duplicating, or inheriting between `Drug` and `Product`. Read this before
touching any code that connects PHAR to SCM/IMS, and update it whenever a decision below changes.

**Ownership boundary (hard rule, extends [PHAR-Drug-Master-Design.md](PHAR-Drug-Master-Design.md)):**
this integration adds **zero schema changes to `Product`, `ItemStock`, or any SCM/IMS entity**. The
only new tables are PHAR's own `Drug` audit columns and one neutral, module-agnostic correlation
table (`PublishedProductLink`) that lives outside both PHAR's and SCM's namespaces.

---

## 1. The problem

- `Drug` (PHAR) is the deliberately isolated clinical/regulatory master — Generic, Brand, Strength,
  Form, TallMan, High-Alert, Controlled Substance, Cold-Chain, Formulary Status. See
  [PHAR-Drug-Master-Design.md](PHAR-Drug-Master-Design.md).
- Every procurement/inventory entity in this codebase — `PurchaseRequisitionItem`,
  `PurchaseOrderProduct`, `ItemStock`, `StockMovement`, `InventoryRequestItem` — converges on a
  **required, non-nullable `ProductId` FK**. There is no abstraction layer; a Pharmacy Store cannot
  raise a Purchase Request today because IMS only knows `Product`, never `Drug`.
- Naive fixes (duplicate every Drug as a Product, merge Drug into Product, inheritance either
  direction) all violate the bounded-context isolation this module was built around, and create
  synchronization problems. Rejected — see §2.

## 2. Rejected approaches

| Approach | Why rejected |
|---|---|
| Duplicate every `Drug` as a `Product` with independently-maintained fields | Two sources of truth for the same clinical identity; drifts the moment either side is edited without the other. |
| Merge `Drug` into `Product` | `Product` is a shared, cross-domain entity (garment/general retail fields — Style, Color, Fabric*, HsCode); forcing clinical fields onto it breaks the bounded context and couples PHAR's schema to SCM's. |
| `Drug` inherits `Product` (or vice versa) | Same coupling as merge, plus fragile EF TPH/TPT mapping across module boundaries. |
| SAP-style "one Material, N Views" (Product as root identity, Drug as a "Pharmacy view" on it) | Real industry pattern (see §3), but requires `Product` to become the root identity for every domain — the opposite of "Drug records stored only in PHAR tables," which is already built and working. Would be a rewrite, not an integration. |

## 3. Industry context

Two legitimate enterprise patterns exist:

- **SAP Material Master / Oracle Item Master** — one shared root identity (Material/Item), with
  Purchasing/MRP/Sales/Batch/Storage *Views* attached per business process. Clean when a single
  system owns the whole item lifecycle. Doesn't fit here (§2, last row).
- **Anti-Corruption Layer + Correlation Identity** (DDD; also how OpenBoxes/mSupply federate
  multi-source drug catalogs, and conceptually how Dynamics 365's Product Information Management
  staging layer works) — each domain keeps its own rich master as the System of Record; a lean,
  generic "shadow" record represents it inside the other system's language, linked by a thin,
  one-directional correlation. **This is the pattern adopted here.**

## 4. The pattern: **Published Product Pattern** (Shadow Product + Anti-Corruption Layer)

```
PHAR                                    SCM/IMS
┌─────────────────────────┐             ┌──────────────────────┐
│ Drug                     │             │ Product               │
│ ------------------------ │  Publish    │ Code, Name, UOM,      │
│ Generic, Brand, Strength,│ ──────────▶ │ MinQty, MaxQty,       │
│ Form, TallMan, HighAlert,│             │ Category="Pharmacy"   │
│ FormularyStatus...       │             │ (nothing else touched)│
│                          │             └──────────┬────────────┘
│ ProductId       Guid?    │                        │
│ PublishedAt     DateTime?│                        ▼
│ PublishedBy     Guid?    │            PR → PO → GRN → ItemStock → Transfer
│ DiscontinuedAt  DateTime?│            (existing SCM/IMS flow, unchanged)
│ DiscontinuedBy  Guid?    │
└─────────────────────────┘
```

**Governing principle:** `Drug` is the System of Record for everything clinical. `Product` is a
System of Reference — a lean shadow that exists only so the *existing, unmodified* SCM/IMS pipeline
can procure and stock a drug. The relationship is **one-directional**: `Drug → Product`, never the
reverse. SCM never knows or needs to know a given `Product` originated from a `Drug`.

## 5. Lifecycle — 3 states, fully derived, no enum

Rejected an explicit `PublishStatus` enum (and a separate `Approved` state) in favor of deriving
state from nullable fields already on `Drug` — matching this codebase's own established principle
that **derived state beats stored state** (see [SCM-RFQ-Lifecycle-Design.md](SCM-RFQ-Lifecycle-Design.md) §1: *"reservation is
DERIVED, never stored"*).

`Approved` was dropped entirely: it had no clear domain owner. Clinical approval already exists as
`Drug.FormularyStatus == Active` (PHAR's own domain); a procurement approval workflow, if ever
needed, belongs to SCM's own approval engine (`ApprovalPolicy`/`ApprovalWorkflow`), not inside the
`Drug` aggregate. Modeling it here would have been premature (YAGNI) and ownerless.

| State | `ProductId` | `PublishedAt` | `DiscontinuedAt` |
|---|---|---|---|
| Never Published | `null` | `null` | `null` |
| Published | not `null` | not `null` | `null` |
| Discontinued | `null` | not `null` | not `null` |

Every combination is unique and valid — no invalid state is representable.

**Publish guard:** a Drug may only be published when `FormularyStatus == Active`. This is a business
rule inside `DrugPublishingService`, not a new state — it reuses PHAR's own existing clinical gate
instead of inventing a parallel one.

## 6. Why the audit fields stay on `Drug`, not on the correlation table

`Drug` keeps `PublishedAt`/`PublishedBy`/`DiscontinuedAt`/`DiscontinuedBy` itself, even though the
correlation table (§7) also timestamps its own creation. This is deliberate, not duplication:

- **Aggregate self-sufficiency (DDD):** an aggregate should answer questions about its own state
  ("When was I published? Who published me? Have I been discontinued?") without joining an external
  integration table. This is exactly what `AuditableEntity`'s own `Created`/`CreatedBy` convention
  already does for every entity in this codebase — no entity relies on a central audit log for its
  own basic history.
- **They answer different questions.** `Drug.PublishedAt` = "when did this business entity enter the
  Published lifecycle state" (a domain fact). `PublishedProductLink.Created` = "when was this
  integration mapping row created" (an infrastructure fact). These usually coincide but are allowed
  to diverge (e.g. a link rebuilt during a future migration) — proof they are not the same fact
  stored twice.
- **Resilience:** if the correlation table is ever rebuilt, re-keyed, or partially cleaned up as pure
  integration plumbing, `Drug` never loses its own business history.

## 7. `PublishedProductLink` — a neutral, generic correlation table

Lives at the root level, like `Product` itself — **not** inside `HMS.Entities.Areas.PHAR` or any SCM
namespace. Its only job is cross-module identity correlation; any future publishing module (Lab,
CSSD, Housekeeping, …) reuses it without touching `Product`'s schema again.

```csharp
// HMS.Entities/PublishedProductLink.cs
public class PublishedProductLink : AuditableEntity
{
    public Guid ProductId { get; set; }        // FK -> Product, unique
    public string SourceModule { get; set; }    // e.g. "PHAR.Drug"
    public Guid SourceEntityId { get; set; }    // e.g. Drug.Id
}
// Unique index: (SourceModule, SourceEntityId)
// Unique index: ProductId
```

**Responsibility split (final):**

| Entity | Owns |
|---|---|
| `Drug` | Its own lifecycle + audit (§6). |
| `PublishedProductLink` | Cross-module identity mapping only. |
| `Product` | Pure procurement/inventory data — no integration metadata, ever. |

## 8. `IProductPublisher` — generic, reusable, transaction-safe

```csharp
public interface IProductPublisher
{
    Task<Guid> PublishAsync(string sourceModule, Guid sourceEntityId, ProductPublishRequest data, Guid userId);
    Task UpdateAsync(string sourceModule, Guid sourceEntityId, ProductPublishRequest data);
    Task DisableAsync(string sourceModule, Guid sourceEntityId);
}
```

Not `IDrugProductPublisher` — the `sourceModule`/`sourceEntityId` parameters make it reusable by any
future module's own UnitOfWork, without touching `Product` or writing a second implementation.

### Transaction boundary — why this avoids a half-published Drug

`ApplicationDbContext` is registered **Transient** in `Startup.cs`. Two separately-injected
UnitOfWork/repository stacks (e.g. a hypothetical `IDrugUnitOfWork` + a separate
`IProductUnitOfWork`) would resolve to **two different `DbContext` instances** — two different
connections, two different transactions. A failure between two independent `SaveChangesAsync()` calls
is exactly how a half-published Drug (`ProductId` set but `Product` row missing, or vice versa) would
happen.

The fix, matching this codebase's own established pattern (`TransCrossMatchUnitOfWork` building
`CrossMatchRepository` **and** `BloodRequestRepository` off the same injected `_context`): the
concrete `ProductPublisher` is constructed **inside `IDrugUnitOfWork`**, sharing the exact same
`_context` field as `DrugRepository` — never a separate UnitOfWork of its own.

```
IDrugUnitOfWork
  ├── DrugRepository         (shared _context)
  ├── DrugGenericRepository  (shared _context)
  └── ProductPublisher       (shared _context)   ← new
```

```
PublishAsync(drug, userId):
    productId = ProductPublisher.PublishAsync("PHAR.Drug", drug.Id, requestFromDrug(drug), userId)
        // stages: new Product row + new PublishedProductLink row — NOT saved yet
    drug.ProductId = productId; drug.PublishedAt = now; drug.PublishedBy = userId
    DrugRepository.UpdateAsync(drug)              // staged
    await _uow.CompleteAsync()                    // ONE SaveChangesAsync() — everything commits
                                                    // or nothing does.
```

No explicit `BeginTransaction()` is needed — EF Core's `SaveChangesAsync()` already wraps every
pending change tracked by one `DbContext` instance into a single database transaction. Because
`Product`, `PublishedProductLink`, and `Drug`'s own update all live in the same change-tracker batch,
a duplicate-code constraint failure (or anything else) rolls back all three together. A half-published
Drug is structurally impossible, not just guarded against.

`ProductPublisher` itself never calls `SaveChangesAsync()` — consistent with every other repository
in this codebase (`Repository<T>.AddAsync`/`UpdateAsync` only stage changes; only `UnitOfWork.CompleteAsync()` persists).

## 9. Field mapping and synchronization policy

| `Product` field | Source | When synced |
|---|---|---|
| `ProductCode` | Newly generated (e.g. `RXP-00001`) | Create only — never changes after (stable identity for PO/GRN history) |
| `ProductName` | Composed: Brand + Strength + Form (+ Generic) | Create + every Update |
| `MeasurementUnitId` | Resolved/created `GeneralConfig` row matching `Drug.DispensingUOM` | Create only |
| `CategoryId` | Pre-seeded "Pharmacy" category | Create only |
| `MinimumQty` / `MaximumQty` | `Drug.ReorderLevel` / `Drug.MaxLevel` | Create + Update |
| `ItemType` | Reuse existing `EnumItemTypes.Material` — no new enum member needed | Create only |
| `IsActive` | `true` on Publish, `false` on Discontinue | Both directions |

**Never synced** (SCM/finance's own domain; `Drug` has no concept of these and never will):
`PurchasePrice`, `UnitPrice`, `Vat`, `PurchaseVat`, `ManufacturerId` (vendor), `StyleId`, `ColorId`,
`FabricLength/Width/Gsm`, `HsCode`, `CountryOfOrigin`, `PackingSize`, `ExpireDate`, `AbcClass` /
`AbcCalculatedOn` / `AbcAnnualValue`, `Details`, `ProductImage`. These stay at their defaults or are
populated entirely by SCM's own processes (e.g. ABC analysis from real purchase history) —
`DrugPublishingService` never touches them, on create or update.

## 10. Post-publish field ownership in SCM's UI

SCM's Product Edit screen checks whether a `PublishedProductLink` row exists for the `Product` being
edited (`WHERE ProductId = @id AND !IsDeleted`). If one exists:

- The synced fields (§9, first table) render **read-only**, with a banner such as *"Synced from
  Pharmacy — edit the Drug record instead."*
- Pricing/vendor/classification fields (§9, "never synced" list) remain **fully editable** by SCM
  users — no divergence risk exists there by construction, since `Drug` never writes to them.
- Enforcement is **UI-level only** (soft), not a DB constraint or trigger — proportionate to the risk,
  and keeps `Product`'s own schema/behavior untouched. This mirrors real ERP UX (SAP greys out
  externally-maintained material fields; Dynamics 365's dual-write sync does the same).

This check is **generic** — it works for any future `SourceModule`, not just `"PHAR.Drug"` — so Lab,
CSSD, or Housekeeping can adopt the same pattern later without a second UI change in SCM.

## 11. Reading stock back — no second ledger

Pharmacy does **not** need its own stock/quantity ledger. Once `ItemStock` receives stock against a
published Drug's `Product`, a future Pharmacy Stock module reads it via:

```sql
ItemStock WHERE ProductId IN (SELECT ProductId FROM phar_drugs WHERE ProductId IS NOT NULL)
```

Quantity's single source of truth stays in IMS (`ItemStock`); clinical metadata's single source of
truth stays in PHAR (`Drug`). The two domains' "truths" never overlap — only a filtered read joins
them.

## 12. Summary — how this answers the original constraints

- ✅ **Zero SCM/IMS schema changes.** `Product`, `ItemStock`, `PurchaseRequisitionItem`, etc. are
  untouched. The only additions are on `Drug` (5 nullable columns) and one new neutral table
  (`PublishedProductLink`).
- ✅ **Pharmacy keeps its own rich `Drug` model**, unmodified from [PHAR-Drug-Master-Design.md](PHAR-Drug-Master-Design.md).
- ✅ **Existing procurement flow is unchanged** — Pharmacy Store's Purchase Request is the existing
  IMS PR screen, scoped to `Category = "Pharmacy"` products; no new PR/PO/GRN entity is needed.
- ✅ **No duplication of business data** — only a thin, one-directional, generic projection (§9)
  crosses the boundary; the rest of `Drug`'s clinical richness never leaves PHAR.
  extend the same `IProductPublisher` + `PublishedProductLink` mechanism.

## 13. Open items for implementation

- `ProductCode` generation rule for Pharmacy-published products (prefix, sequence source).
- Which `GeneralConfig` UOM rows exist today vs. need seeding for common dispensing units.
- Whether "Approved" ever needs SCM's `ApprovalWorkflow` engine — explicitly deferred (§5); revisit
  only if a real procurement-approval requirement appears.
- Re-publish behavior after a Discontinue (new `Product`/`PublishedProductLink` row vs. reactivating
  the old one) — not yet decided; default to creating fresh unless reactivation proves necessary.
