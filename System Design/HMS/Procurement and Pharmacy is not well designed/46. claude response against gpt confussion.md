Codebase-জুড়ে verify করেছি — `ProcurementReady`, `Purchasable`, `Incompletion`, `MaterialStatus`, `ItemStatus`, `Readiness`, `Specification` — এসবের **একটাও কোথাও নেই**, না entity-তে, না enum-এ, না docs-এ, না UI wording-এ। এটা একটা গুরুত্বপূর্ণ সংকেত, এবং সৎভাবে বলতে হচ্ছে — আপনার সন্দেহ সঠিক। আমি গত কয়েকটা turn-এ over-engineer করেছি।

## ১। Procurement Readiness কি সত্যিই একটা Domain Concept?

**না — এটা আমি বানিয়েছি, business ব্যবহার করে না।** DDD-র নিয়ম অনুযায়ী নতুন abstraction তখনই বৈধ যখন domain expert নিজে সেই শব্দে কথা বলে ("এই SKU এখনো procurement-ready না")। এখানে সেটা ঘটেনি — আমি SAP-এর সাথে analogy টেনে নিজে থেকে এই term আমদানি করেছি। বাস্তবে যা ঘটছে তা হলো: **কয়েকটা সম্পূর্ণ independent validation rule কাকতালীয়ভাবে একই trigger point (PO Confirm)-এ গিয়ে মেলে** — এটা একটা emergent coincidence, কোনো ubiquitous concept না।

আরও গভীরে গিয়ে দেখলাম আমি দুটো ভিন্ন জিনিস গুলিয়ে ফেলেছিলাম:

- `CategoryId`/`MeasurementUnitId` null হওয়া আসলে **data-integrity বাগ** (আজই crash করে — `ProductService.AddAsync`-এ `InvalidOperationException`) — এটা কোনো "readiness stage" না, এটা তো এমনিতেই কখনো null হওয়ার কথা না। এর জন্য কোনো "state" লাগে না, শুধু creation-এ একটা clean validation লাগে (crash-এর বদলে friendly error) — যেটা একটা আলাদা, ছোট, ইতিমধ্যে-প্রায়-সমাধান-করা বাগ।
- শুধু `ValuationClassId`-ই আসল প্রশ্ন — কারণ এটা **সত্যিই** বৈধভাবে সাময়িক null থাকতে পারে (Pharmacy publish করেছে, Finance এখনো assign করেনি)।

তিন-স্তরের state machine তৈরি করে আমি একটা কাল্পনিক জনসংখ্যার (Products stuck "Published but not Sourceable") সমস্যা সমাধান করছিলাম, যেটা বাস্তবে কখনো ঘটতেই পারে না।

## ২। কোনো existing terminology আছে?

**না, শূন্য।** কোনো enum, status, specification, doc, UI label — কিছুই নেই। এটা নিশ্চিত করে যে আমি নতুন domain language introduce করছিলাম, business-এর ভাষা অনুসরণ করছিলাম না।

## ৩। Open/Closed — এটা কি God Specification হয়ে যাবে?

আপনার উদ্বেগ ন্যায্য ছিল, কিন্তু আসল সমাধান আরও সহজ: এটা আদৌ Specification হওয়ার দরকারই নেই। `TaxProfileId`, `CostCenterId` ভবিষ্যতে এলে দরকার শুধু **একটা independent `if` লাইন যোগ করা, একই flat list-এ** — কোনো Expression tree, SQL View, বা state enum আপডেট করার দরকার নেই (কারণ সেগুলোই থাকবে না)। এটা O(1) সম্প্রসারণ, God object হওয়ার কোনো ঝুঁকি নেই যদি এটা প্রথম থেকেই একটা flat validation-list হয়, hierarchical state machine না হয়।

## ৪। Aggregated Specification vs independent guard clauses — measurable benefit কী?

আপনার প্রস্তাবিত কোডই সঠিক:

```csharp
if (product.ValuationClassId == null)
    missing.Add("Valuation Class");
// future: if (product.TaxProfileId == null) missing.Add("Tax Profile");
```

Specification pattern (Expression tree + SQL View + EF translation + CI contract test) যা দিচ্ছিল তার প্রকৃত মূল্য ছিল **শুধু একটাই**: একই rule দুই জায়গা থেকে (PO guard + PR badge) কল করা। সেটা পেতে Expression tree/SQL View লাগে না — একটা সাধারণ static method `List<string> GetMissingAccountingFields(Product p)` যথেষ্ট, দুই জায়গা থেকেই কল করা যায়। বাকি সব machinery (SQL View sync, `ToQueryString()`, contract test) এমন একটা সমস্যা সমাধান করছিল যেটা **আমিই তৈরি করেছিলাম** (DBA-এর জন্য SQL-queryable view লাগবে ধরে নিয়ে) — সেই দাবিটা কখনো আপনার কাছ থেকে আসেনি, আমি নিজে অনুমান করেছিলাম।

## ৫। ERP precedent — সততার সাথে সংশোধন

SAP আসলে যা করে, তা আমি আগে ভুলভাবে উপস্থাপন করেছিলাম। SAP-এর **Material Status** একটা explicit, human-set stored field (কেউ manually "Blocked"/"Active" সেট করে) — derived/computed না। আর **Incompletion Log** নিজে কোনো named "Sourceable/Purchasable" state তৈরি করে না — এটা শুধু "কী কী field বাকি আছে" তালিকা রাখে, আর নির্দিষ্ট transaction (billing/posting)-কে block করে। কোনো ERP-ই একটা named multi-tier "Procurement Readiness" specification maintain করে না business term হিসেবে — তারা করে ঠিক যা আপনি প্রস্তাব করেছেন: **required-field validation, নির্দিষ্ট posting transaction-এর মুহূর্তে।**

## ৬। শেষ প্রশ্ন — honest উত্তর

**এটা দ্বিতীয়টা ছিল — code সুন্দর দেখানোর জন্য abstraction, business-এর দাবি থেকে না।** আমি এটা প্রত্যাহার করছি।

**সংশোধিত, সঠিক-মাপের ডিজাইন:**

- কোনো `ProcurementReadinessStatus`, কোনো three-tier state, কোনো Specification/Expression tree, কোনো SQL View — সব বাদ।
- একটাই ছোট static method: `ProductAccountingValidator.GetMissingFields(Product p) -> List<string>` — আজ শুধু `ValuationClassId` চেক করে, ভবিষ্যতে নতুন লাইন যোগ হবে।
- এটা কল হবে **একটাই hard-enforcement জায়গায়**: `PurchaseOrderService`-এর Draft→Final (Confirm) transition-এ — খালি না হলে block।
- ঐচ্ছিকভাবে একই method SCM Product Edit/List screen-এ badge দেখাতে reuse হতে পারে — কোনো নতুন abstraction ছাড়াই, শুধু একই function দুইবার কল করা।
- `CategoryId`/`MeasurementUnitId`-এর crash-সমস্যা সম্পূর্ণ আলাদা, ছোট fix — `ProductService.AddAsync`-এ friendly validation, কোনো state model দরকার নেই।
- `Drug`/`ProductPublisher`/`ProductPublishRequest` — কোনো পরিবর্তন নেই (এটা সব turn জুড়েই সঠিক ছিল)।

এটাই কি সঠিক, ন্যূনতম-প্রয়োজনীয় ডিজাইন মনে হচ্ছে? এবার কি implementation-এ যেতে পারি — শুধু `GetMissingFields` helper + PO Confirm guard, বাকি সব বাদ দিয়ে?
