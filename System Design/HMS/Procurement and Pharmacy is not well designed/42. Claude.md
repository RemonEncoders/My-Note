আপনি ঠিক ধরেছেন — আমি নিজের বলা নীতির সাথেই সাংঘর্ষিক প্রস্তাব দিয়েছিলাম। এটা swept-under-the-rug করব না; সংশোধন করছি।

## কোথায় ভুল হয়েছিল

`Product.AbcClass`-এর precedent টেনেছিলাম, কিন্তু সেটা আসলে ভিন্ন শ্রেণীর জিনিস — `AbcClass` **periodically ব্যাচ-রিক্যালকুলেটেড** (`RunAbcAnalysisAsync`, ম্যানুয়াল ট্রিগার, staleness expected এবং acceptable — "as of" timestamp-ই তার প্রমাণ)। কিন্তু `ProcurementReadinessStatus` এমন একটা invariant যেটা **সবসময় real-time সঠিক থাকতে হবে**, কারণ PO Confirm guard এর উপর নির্ভর করবে। এই দুটো এক জিনিস না — আমি ভুল precedent টেনেছিলাম। আপনার তিনটা sub-প্রশ্নই (drift risk, principle violation, write-path guarantee) সম্পূর্ণ বৈধ।

## সংশোধিত design: materialized column বাদ, তার বদলে একটা SQL View

তিনটা বিকল্প বিবেচনা করে যেটাতে পৌঁছেছি:

|বিকল্প|সমস্যা|
|---|---|
|Materialized enum column + app-code recompute|ঠিক যা আপনি ধরেছেন — প্রতিটা write path মনে রাখতে হবে, ভুলে গেলে silent drift|
|SQL Server `PERSISTED COMPUTED COLUMN`|Engine-level guarantee (raw SQL bাইপাসও নিরাপদ), কিন্তু formula দুইবার লিখতে হয় — migration-এর SQL string-এ, আর C#-এর `MandatoryForPurchasable`-এ — দুটো ভাষায় duplicate|
|**একটা plain SQL View (recommend)**|কোথাও কিছু stored হয় না — প্রতি query-তে recompute|

**সঠিক উত্তর: কোনো column-ই দরকার নেই — একটা database View।**

```sql
CREATE VIEW vw_ProductProcurementReadiness AS
SELECT
    p.Id,
    CASE
        WHEN p.CategoryId IS NULL OR p.MeasurementUnitId IS NULL THEN 'NotSourceable'
        WHEN p.ValuationClassId IS NULL /* future: OR p.TaxProfileId IS NULL ... */ THEN 'Sourceable'
        ELSE 'Purchasable'
    END AS ReadinessStatus
FROM Products p WHERE p.IsDeleted = 0
```

এটা **"derived state, never stored"** নীতিকে সবচেয়ে বিশুদ্ধ রূপে মেনে চলে — View কিছুই persist করে না, প্রতিটা `SELECT` নিজেই live recompute করে। DBA/Report/PowerBI/Crystal — সবাই সরাসরি এই View query করতে পারবে, কোনো app-code বা cache staleness ছাড়াই। Application-side সিদ্ধান্তগুলো (PR/RFQ badge, PO Confirm guard) View-ও পড়বে না — সরাসরি C#-এর `Classify()` কল করবে লোড করা `Product` entity-র উপর, live। মানে দুই ধরনের consumer, দুই mechanism, কোনোটাই কিছু "store" করে না।

## চারটা sub-প্রশ্নের সরাসরি উত্তর

**১. `Classify()`-এর একমাত্র authoritative জায়গা কোথায়?** একটা pure, static Domain Specification class — `HMS.Entities/Policies/ProductProcurementReadinessPolicy.cs` — DI নেই, DB call নেই, শুধু `Product -> ProcurementReadinessStatus`। এটা `HMS.Common.Enums`-এ `PurchaseOrderStatuses.Reserving`-এর ঠিক পাশের প্যাটার্ন ([EnumPurchaseOrderStatus.cs:41-52](vscode-webview://0tri44ar51et483btke71i178mqksugck1rce8n1q6b1u371eioe/HMS.Common/Enums/EnumPurchaseOrderStatus.cs#L41-L52)) — policy logic entity/enum-এর পাশে static class হিসেবে থাকে, কখনো Service-এর ভেতরে গুঁজে দেওয়া হয় না। এই কোডবেসেই এর precedent বিদ্যমান।

**২. প্রতিটা write path recompute করবে তার guarantee কী?** প্রশ্নটাই আর প্রযোজ্য না — কারণ কিছুই "recompute করে store" করা হচ্ছে না। SCM Add/Edit, Pharmacy Publish, Excel Import, Bulk Update, ভবিষ্যতের API — কেউই `ProcurementReadinessStatus` লিখবে না, কারণ সেই column-ই নেই। PO Confirm guard যখন সিদ্ধান্ত নেয়, তখন সেই মুহূর্তের `Product` entity-র উপর সরাসরি `Classify()` চালায় — সবসময় বর্তমান field-value-র উপর ভিত্তি করে, কখনো stale হওয়ার সুযোগ নেই। "মনে রাখতে হবে" জিনিসটাই architecture থেকে বাদ পড়ে গেছে।

**৩. Domain Specification/Policy, না ProductService helper?** Domain Specification/Policy — নিশ্চিতভাবে। কারণ এটাকে Razor view (badge render), `PurchaseOrderService` (guard), এবং ভবিষ্যতে test suite (নিচে দেখুন) — তিন জায়গা থেকেই কল করতে হবে, কোনো DI dependency ছাড়া। `ProductService`-এর ভেতরে রাখলে সেই reusability ভেঙে যেত।

**৪. নতুন field এলে কোনো code path যেন ভুলে না যায়, সেটা কীভাবে নিশ্চিত করব?** "মনে রাখা"-র উপর নির্ভর না করে, একটা **CI-তে চলা contract test** দিয়ে:

```
[Test] // চলে প্রতি build-এ
void PolicyAndViewMustAgree()
{
    foreach (var scenario in SyntheticProductRows) // সব null-combination cover করে
    {
        var cSharpResult = ProductProcurementReadinessPolicy.Classify(scenario);
        var sqlResult   = QueryView("vw_ProductProcurementReadiness", scenario.Id);
        Assert.Equal(cSharpResult, sqlResult);
    }
}
```

নতুন field যোগ করলে দুটো জিনিস **একই migration-এ** পাশাপাশি বদলাতে হয়: (ক) `MandatoryForPurchasable`-এ এক লাইন, (খ) View-এর `CASE` expression-এ এক শর্ত। কেউ একটা করে অন্যটা ভুলে গেলে এই test build-এ fail করবে — guarantee টা মানুষের discipline না, একটা ব্যর্থ build।

---

এটা কি এখন "derived state, never stored" নীতির সাথে সামঞ্জস্যপূর্ণ মনে হচ্ছে? মিললে আগের authoritative table আর `IsPurchasable` pseudocode-এ শুধু একটা পরিবর্তন দরকার — `Product.ProcurementReadinessStatus` column-এর জায়গায় `vw_ProductProcurementReadiness` view বসবে, বাকি সব অপরিবর্তিত থাকবে।
