সঠিক প্রশ্ন — এবং এটা আসলে আপনার নিজের কোডবেসেই ইতিমধ্যে প্রতিষ্ঠিত একটা নীতির সাথে মেলে। RFQ reservation ডিজাইনে আপনি আগেই এই সিদ্ধান্ত নিয়েছিলেন: _"reservation is DERIVED, never stored — there is no `ReservedQty` column anywhere, and there never may be"_ ([SCM-RFQ-Lifecycle-Design.md](vscode-webview://0tri44ar51et483btke71i178mqksugck1rce8n1q6b1u371eioe/docs/SCM-RFQ-Lifecycle-Design.md)-এ)। এখানেও ঠিক একই যুক্তি প্রযোজ্য — derived state জিতবে।

## হ্যাঁ, derived approach ভালো — কিন্তু একটা gap আছে

শুধু `ProductId` + `PublishedAt`/`PublishedBy` দিয়ে **৪টা state** পুরোপুরি derive করা যায় না। সমস্যাটা এখানে:

```
Draft:        ProductId == null, PublishedAt == null   ← ঠিক আছে
Published:    ProductId != null                          ← ঠিক আছে
Discontinued: ProductId == null, PublishedAt != null    ← কিন্তু এটা Draft থেকে আলাদা করে কীভাবে?
```

`Discontinued` আর `Draft` — দুটোতেই `ProductId == null`। শুধু `PublishedAt` দিয়ে এটা ঠিকভাবেই আলাদা হয় (Draft-এ কখনো publish হয়নি, তাই `PublishedAt == null`; Discontinued-এ একবার publish হয়েছিল, তাই `PublishedAt != null`) — **আসলে এইটুকুতেই কাজ চলে যায়, যদি "Discontinued" মানে হয় শুধু "আগে একবার publish হয়েছিল, এখন নেই"।**

কিন্তু `Approved` state-টা যোগ করলে সমস্যা হয় — Approved-এও `ProductId == null`, `PublishedAt == null`, কিন্তু Draft থেকে আলাদা হতে হবে। এর জন্য একটা তৃতীয় audit pair লাগবে: `ApprovedAt`/`ApprovedBy`।

**পূর্ণ derivation টেবিল:**

|State|ApprovedAt|ProductId|PublishedAt (সর্বশেষ)|
|---|---|---|---|
|Draft|null|null|null|
|Approved|not null|null|null|
|Published|(irrelevant)|not null|not null|
|Discontinued|(irrelevant)|null|not null|

তিনটা nullable audit pair (`ApprovedAt/By`, `PublishedAt/By`, `DiscontinuedAt/By`) — এটা নতুন কোনো ধারণা না, `AuditableEntity`-র `Created/CreatedBy`, `LastModified/LastModifiedBy`-র একই idiom-এর সম্প্রসারণ মাত্র। কোনো enum লাগে না, কোনো invalid combination সম্ভবই না (কারণ state fields-এর function, stored value না)।

## আপনার প্রশ্নের সরাসরি উত্তর: enterprise-এ dedicated PublishStatus কখন সত্যিই দরকার

সৎভাবেই বলি — কিছু বাস্তব পরিস্থিতিতে dedicated status column derived-এর চেয়ে ভালো:

1. **Non-linear / branching state graph** — যদি ভবিষ্যতে "Recalled" (Discontinued থেকে আলাদা, dispensing-ও ব্লক করে) বা "On Hold" (vendor confirmation পেন্ডিং)-এর মতো state যোগ হয় যেগুলো একটা সরল ৪-ধাপের chain-এ পড়ে না, তখন derivation logic জটিল nested condition হয়ে যায় — সেখানে explicit enum + state-transition-guard function পড়া সহজ হয়।
2. **BI/reporting-heavy সিস্টেম** — বড় ডেটা ওয়্যারহাউজ/Power BI-জাতীয় টুলে analyst-রা `GROUP BY Status` করতে চান, প্রতিটা রিপোর্টে derivation logic পুনরাবৃত্তি করতে চান না। এই স্কেলে (হাজার-দশেক ড্রাগ) এটা বাস্তব সমস্যা না।
3. **Legacy data migration** — যেখানে আপনি জানেন বর্তমান status কী, কিন্তু ঠিক কবে সেই transition হয়েছিল তা জানেন না — তখন status আর timestamp-কে decouple করা দরকার হয়।
4. **SAP-ধরনের Status Management ইঞ্জিন** যেখানে workflow engine নিজেই explicit status object আশা করে — এটা মূলত platform constraint, pure architecture যুক্তি না।

**আপনার কেসে এর একটাও প্রযোজ্য না** — lifecycle সরল/linear, স্কেল ছোট, কোনো heavyweight workflow engine বাধ্যতামূলক না। তাই derived approach-ই সঠিক সিদ্ধান্ত।

## একটা ছোট flag (এখনই সিদ্ধান্ত না নিলেও চলবে)

এই তিনটা audit pair শুধু **সর্বশেষ transition** ধরে রাখে (`LastModified`-এর মতোই) — যদি কখনো Publish→Discontinue→Republish→Discontinue চক্র চলে, মাঝের ইতিহাস হারিয়ে যাবে। Pharmacy/regulatory context-এ পূর্ণ audit trail দরকার হতে পারে ভবিষ্যতে (annual review-এর মতোই)। এখনকার জন্য "latest-only" (বাকি প্রজেক্টের কনভেনশন) যথেষ্ট ধরে নিচ্ছি — যদি full history লাগে, সেটা আলাদা `DrugPublishHistory` টেবিল হবে, `Drug`-এর ফিল্ড না। এটা এখনই সিদ্ধান্ত নেওয়ার দরকার নেই, implementation-এর সময় সহজেই যোগ করা যাবে।
