# আমি Claude-কে এভাবে বলতাম

I think we need to distinguish between two different kinds of validation.

Some fields are workflow-specific and belong to the SCM manual product creation experience, for example:

- ABC Classification
    
- Preferred Vendor
    
- Last Purchase Price
    

Those can legitimately be completed later.

However, other fields are not UI concerns at all—they are enterprise business invariants.

For example, if every inventory transaction and every accounting posting requires a Valuation Class (or Accounting Class), then a Product without a Valuation Class is not merely "procurement-incomplete"; it is business-invalid.

In that case, I want the Pharmacy publishing flow to enforce exactly the same rule as the SCM Product Add flow.

My requirement is:

- If a field represents a true enterprise invariant that every Product must satisfy regardless of how it is created, then that field and its validation must exist in the Pharmacy Drug UI and in the Pharmacy service layer as well.
    
- If a field is only relevant to the SCM manual workflow, then it can remain outside the Pharmacy publishing process.
    

Can you analyze every field currently validated in the SCM Product Add screen and classify them into these two categories?

1. Enterprise Product Invariants (must be enforced by every Product creation path, including Pharmacy publishing).
    
2. SCM Workflow-specific attributes (only required for manual SCM product management).
    

I want this classification before implementation because I do not want two creation paths producing Products with different business validity.

এই প্রশ্নটা Claude-কে করলে সে আর generic architecture উত্তর দেবে না। তাকে **প্রতিটি field** (Valuation Class, Measurement Unit, Category, Product Importance, Vendor, VAT, Price, ইত্যাদি) বিশ্লেষণ করে বলতে হবে কোনটা **enterprise invariant** আর কোনটা **SCM-specific workflow field**। এই classification-টাই তোমার implementation-এর জন্য সবচেয়ে গুরুত্বপূর্ণ।
