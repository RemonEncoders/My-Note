যাচাই পদ্ধতি
শুধু "UI-তে required লেখা আছে" দেখে classify করিনি — কারণ SCM-এর নিজের Add screen-এও required মার্কিং misleading হতে পারে (যেমন নিচে দেখাচ্ছি)। বরং প্রতিটা ফিল্ডের জন্য পরীক্ষা করেছি:

যদি এই ফিল্ড null থাকে, downstream-এ কী ঘটে — silent data corruption/broken invariant, নাকি কোড নিজেই gracefully default করে দেয়?

প্রথমটা হলে সেটা enterprise invariant, দ্বিতীয়টা হলে সেটা workflow convenience।

এই টেস্ট প্রয়োগ করে একটা concrete গর্ত পেয়েছি — যেটা ঠিক আপনার দেওয়া উদাহরণের (Valuation Class) সাথেই মিলে যায়:

Product.ValuationClassId null হলে অ্যাকাউন্টিং পোস্টিং silently ভেঙে যায় — hypothesis নয়, প্রমাণিত:

MaterialGLFindService.cs:19-21 — ValuationClassId null হলে Guid.Empty রিটার্ন করে।
MaterialGLFindService.cs:44-51 — সেই Guid.Empty দিয়ে ValuationClassTransactions টেবিলে GL mapping খোঁজে, মিল না পেলে mtGl == null, তখন drGl = crGl = Guid.Empty।
GoodsReceiveService.cs:427-443 — এই Guid.Empty কোনো check ছাড়াই সরাসরি JournalEntryItem.GlMasterId-তে বসে যায়।
মানে: Pharmacy-published কোনো Product-এর বিপরীতে Goods Receive হলে, journal entry তৈরি হবে empty GL account রেফারেন্স দিয়ে — কোনো exception ছাড়াই। এটা ঠিক আপনি যা আশঙ্কা করেছিলেন তাই — procurement-incompleteness নয়, সরাসরি business-invalid state।

বিপরীতে, UnitPrice (Sales Price) SCM-এর Add screen-এ required মার্ক করা থাকলেও, ProductModel.cs:234 নিজেই this.UnitPrice ?? 0 করে ফেলে — কোড নিজেই null-কে gracefully 0 বানিয়ে দিচ্ছে। তাই HTML-এ required থাকলেও এটা প্রকৃত invariant নয়, নিছক data-entry discipline।

সিদ্ধান্ত — একমাত্র প্রকৃত গ্যাপ: ValuationClassId
Category ১-এর বাকি সবগুলো ফিল্ড ইতিমধ্যেই ProductPublisher পূরণ করে দেয় — কোনো ফিক্সের দরকার নেই। শুধু ValuationClassId-ই সত্যিকারের এন্টারপ্রাইজ ইনভেরিয়েন্ট যেটা এখনো missing, এবং এটা বন্ধ করতে হলে:

Drug entity-তে একটা নতুন column যোগ (ValuationClassId) — এটা Product schema-তে নয়, Drug-এর নিজের schema-তে, তাই design doc-এর "zero Product schema change" নিয়ম ভাঙে না।
PHAR-এর Drug Add/Edit UI-তে একটা "Valuation Class" dropdown যোগ (ঠিক SCM-এর "Acc Group" dropdown-এর মতো)।
DrugService.PublishAsync-এ একটা guard যোগ — ঠিক বর্তমান FormularyStatus != Active guard-এর (DrugService.cs:95-96) মতো প্যাটার্নে — Drug.ValuationClassId == null হলে publish আটকে দেবে।
ProductPublishRequest-এ ValuationClassId যোগ (ProductPublishRequest.cs) এবং ProductPublisher.PublishAsync-এ সেটা Product.ValuationClassId-তে বসানো।
এটা করলে SCM manual path আর PHAR publish path — দুটোই একই invariant মানবে, কোনো duplication বা নতুন coupling ছাড়াই।

এই classification-টা কি আপনার প্রত্যাশার সাথে মেলে, নাকি অন্য কোনো ফিল্ড আপনি Category ১-এ নিতে চান? মিললে আমি উপরের ৪-ধাপের implementation plan নিয়ে এগোতে পারি।
