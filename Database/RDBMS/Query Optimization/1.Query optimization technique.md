# আগে কখনো “কাজ না করা” একটি Database-কে আমি কীভাবে Optimize করি

সম্প্রতি একটি Database optimization করার সময়, একটি গুরুত্বপূর্ণ টেবিলে মাত্র **একটি Index পরিবর্তন** করেই একটি Query-এর **200,000-এর বেশি logical reads কমিয়ে 10-এ** নামিয়ে আনতে পেরেছি। একই execution path-এর সঙ্গে সম্পর্কিত আরও কয়েকটি report query-এর performance-ও **90–99% পর্যন্ত উন্নত হয়েছে**।

কোনো application code পরিবর্তন করতে হয়নি। কোনো business requirements meeting-এরও প্রয়োজন হয়নি। শুধু data-ই আমাকে ঠিক কোথায় সমস্যা হচ্ছে তা দেখিয়েছে।

এখানে যে বিষয়টি মানুষকে অবাক করে তা হলো: ওই Query-গুলোর business logic কী, তা আমি জানতাম না।

আমাকে প্রায়ই জিজ্ঞেস করা হয়:

> “কোনো application-এর database কীভাবে দ্রুত করবে, যখন তুমি জানোই না application-টি কী কাজ করে?”

সত্যি কথা হলো, আমি business logic দিয়ে শুরু করি না। আমি **evidence** বা প্রমাণ দিয়ে শুরু করি।

সাধারণত আমার process এমন হয়:

### ১. Query Store data সংগ্রহ করি

অথবা সমমানের execution log থেকে নিচের তথ্যগুলো দেখি:

- Query text
    
- Average duration
    
- Average CPU
    
- Average logical reads
    
- Execution count
    

### ২. শুধু মোট সময় নয়, প্রতি execution-এর cost অনুযায়ী Query-গুলোকে Rank করি

একটি Query দিনে দুইবার চলে এবং প্রতিবার 90 সেকেন্ড সময় নেয়, আরেকটি Query দিনে 50,000 বার চলে এবং প্রতিবার 0.3 সেকেন্ড সময় নেয়—দুটিই আসল bottleneck হতে পারে।

তাই দুটোকেই বিবেচনা করতে হবে।

### ৩. “Smoking gun” Query খুঁজি

অর্থাৎ এমন Query খুঁজি যার reads বা duration, Query-টি যা করার কথা তার তুলনায় অস্বাভাবিকভাবে বেশি।

এই ধরনের mismatch প্রায়ই নিচের সমস্যাগুলোর কারণে হয়:

- Missing index.
    
- খারাপ বা inefficient join.
    
- Hidden N+1 pattern.
    
- Lazy loading.
    
- ORM-generated অতিরিক্ত database round trips.
    

### ৪. একটি নির্দিষ্ট এবং targeted fix প্রস্তাব করি

সাধারণত একটি **covering index** হতে পারে।

তবে পরিবর্তন করার আগে আমি অনুমান করি যে এই পরিবর্তনের ফলে কী ধরনের performance improvement আশা করা যায়।

### ৫. পরিবর্তনের পর আবার data সংগ্রহ করে তুলনা করি

আমি **apples to apples** comparison করি।

অর্থাৎ শুধু raw total দেখি না, বরং দেখি:

- Average reads per execution
    
- Average milliseconds per execution
    

কারণ দুইটি capture window কখনোই সম্পূর্ণ একই রকম হয় না।

---

## মূল ধারণাটি হলো:

একটি Query কেন business-এর জন্য প্রয়োজনীয়, সেটা বুঝতেই হবে—এমন নয়।

তোমাকে বুঝতে হবে:

> **Query-টি কতটা expensive এবং কেন expensive।**

Execution plan এবং wait statistics তোমার domain knowledge-এর ওপর নির্ভর করে না। এগুলো শুধু দেখায় database engine কোথায় প্রয়োজনের তুলনায় বেশি কাজ করছে।

সময়ের সঙ্গে business context জানা একজন optimizer-কে আরও ভালো করে তোলে।

কিন্তু database-এর প্রথম **80% performance problem** খুঁজে বের করে ঠিক করার ক্ষেত্রে business logic সম্পর্কে গভীর জ্ঞান থাকা সাধারণত বাধা নয়।
